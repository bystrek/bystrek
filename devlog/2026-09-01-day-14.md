# Day Fourteen — bystrek.dev

**Date:** 2026-09-01
**Goal:** Decide whether to pivot from PWA-only to a Capacitor-wrapped native iOS build distributed via EU sideloading (AltStore PAL). Sparked by "PWA is not going to cut it" — Apple's constrained web push, unreliable background delivery, and no home-screen presence beyond the icon on iOS were the felt pain points, even if not spelled out this session.

## What we decided

**Stay PWA-only for now. No Capacitor, no App Store, no AltStore PAL, no Apple Developer Program enrollment.** The pivot got walked through end-to-end before being rejected — not dismissed on vibes. The cost side turned out much heavier than "wrap the SvelteKit build with Capacitor and ship":

- **AltStore PAL still requires Apple Developer Program membership ($99/yr, recurring).** The DMA forced Apple to open *distribution* (marketplaces, Web Distribution) but Apple kept the *trust chain* — every alt-marketplace app must still be notarized by Apple and signed with a Developer Program certificate. AltStore only handles the distribution UI; it can't sign or notarize on your behalf. Free paths (AltStore Classic, Xcode direct install with a personal Apple ID) all exist but every one of them has APNs gated behind the paid membership, and push is bystrek's entire point — so those don't apply.
- **Web Distribution (self-host the .ipa from bystrek.dev) needs a legal entity "registered in the EU."** A Polish JDG is a registered business but not a separate legal person from the owner; Apple's docs are ambiguous, real-world reports are mixed. Not a clean yes, and enrolling as Organization via JDG's D-U-N-S also puts the personal legal name on Apple's records (JDG has no separate legal name — only the *firma* trade name sits on top for public seller display).
- **Stack impact is real, not "same stack + a wrapper."** SvelteKit would need `adapter-static` for the Capacitor bundle (either dual-build with the droplet's current adapter, or move fully static). Web Push (VAPID) doesn't work inside a Capacitor shell — `api` would need an APNs sender path (`node-apn` with a p8 key or a service), and the subscribe flow would fork by client. Live Updates (Capgo self-hosted or Ionic's) becomes near-mandatory or every UI tweak means notarize + redistribute.
- **EU regulatory ceiling isn't moving.** The Commission's active DMA non-compliance case against Apple targets the Core Technology Fee and anti-steering rules, not the $99 base fee or Apple's exclusive control of notarization/signing. The $99 is treated as legitimate platform cost. No near-term shift will change the calculus above.

Weighed against the reasons for pivoting (better push, home-screen presence, real background behavior on iOS), the PWA's shortcomings weren't yet dear enough to justify $99/yr forever, an Apple identity trail on top of the deliberately-non-identifying [[project_domain_identity|bystrek.dev]] setup, a stack fork (VAPID + APNs both, or migrate off VAPID entirely), and the ongoing notarize-per-release friction. Revisit once the audience or the felt pain grows past what PWA can carry.

**Alternatives surveyed and rejected:**
- **Capacitor + AltStore PAL (unlisted source at bystrek.dev/altstore-source.json), Individual Apple Developer account.** The cleanest paid path — no EU entity needed, seller identity effectively private since the source is URL-only. Rejected on the $99/yr + APNs stack fork combination, not on the distribution path itself.
- **Capacitor + Web Distribution direct from bystrek.dev, Organization account via JDG D-U-N-S.** More self-contained (no marketplace), and the JDG's *firma* would appear as the public seller instead of the personal name. Rejected on the JDG-as-legal-entity ambiguity plus the same underlying $99 + stack costs.
- **AltStore Classic (non-PAL, global, personal Apple ID, free provisioning, 7-day cert refresh).** $0, no name to Apple. Rejected because APNs auth keys are paid-account-only regardless of how the app got installed, so it can't do push at all — a non-starter for bystrek specifically.

Nothing. This session was a design decision only — no code, no config, no dependency changes.

## Continuation: fix #22 chat opens scrolled to top (2nd session, same day)

### What we decided

**Root cause is `ngAfterViewChecked` not firing on signal-driven DOM updates in zoneless mode.** The auto-scroll was hung off that lifecycle hook, but with `provideZonelessChangeDetection()` an async signal update (history arriving from the network) patches the DOM through the reactive graph without running the classic view-checked lifecycle. Confirmed by instrumenting the hook: it fires exactly twice on component init (both times with empty messages, matching `lastRenderedMessages = ''`), then never again — including on the render that appends the 30 seeded history bubbles.

Considered fixes:
- **Direct `container.scrollTop = container.scrollHeight` in `loadHistory` after the signal set.** Simple, but couples a service to a specific DOM layout, and would need a separate second call for every future signal path that changes messages (streamed chunks, error retries).
- **`effect()` reading `chat.messages()` and calling `scrollIntoView`.** Reacts to the right thing, but `effect()` runs synchronously after the signal change and before the render, so the anchor's post-append position isn't there yet — you'd need a nested `queueMicrotask`/`requestAnimationFrame`.
- **`afterRenderEffect` reading `chat.messages()`.** Runs after each render whose reactive deps changed, on the correct side of the render boundary — no manual scheduling, and it works identically for history-load, send-user-message, and streamed assistant chunks because they all funnel through the same signal. Picked this.

Kept the `lastRenderedMessages` snapshot and the `pinnedToBottom` intent flag as-is — the snapshot still matters because `afterRenderEffect` will run on every render that reads `messages()` including keystrokes in the input (both live in the same component, and typing re-runs the template because `[ngModel]="draft()"` re-reads state on the same view), and the "am I at the bottom" tracking still can't be re-measured post-append.

### What we actually built

- `ui/src/app/features/chat/chat.ts` — replaced `ngAfterViewChecked` with `afterRenderEffect` in the constructor. Same guard logic (snapshot diff + `pinnedToBottom` check + `scrollIntoView({ block: 'end' })` on the anchor). Removed the `AfterViewChecked` import/interface.
- `ui/e2e/chat.spec.ts` — added a regression test that seeds 30-message history via the mock route, then asserts `.bubble` last-child is in the viewport. It fails against the old code (last bubble is ~2600px off-screen below the fold) and passes on the fix.

Verified in-browser: `.messages` container reports `scrollTop: 2664` / `scrollHeight: 3360` / `clientHeight: 696` on load with 30 seeded messages — pinned to the very bottom. All three chat e2e tests green, `tsc --noEmit` clean.

### Problems hit along the way (and the actual fixes)

- **Repro was tricky to see just from reading the code**, because the pattern looked correct against classic zone-based Angular — signal → CD → template updates → lifecycle. Needed console.log tracing inside `ngAfterViewChecked` to confirm it only fires on the two initial passes and never again after history lands. Once that was visible, the zoneless connection to `provideZonelessChangeDetection()` was one grep away.
- **`scrollIntoView` on the anchor works correctly when called manually** — verified by running it via Playwright's `page.evaluate` on the bugged build, which moved `scrollTop` from 0 to 2664. That ruled out a layout/CSS bug (e.g. the wrong element being the scroll container) and pointed the finger cleanly at the "who's supposed to call it" question.

## Continuation: fix #24 iOS Safari auto-zooms chat input (3rd session, same day)

### What we decided

**Root cause is the well-known iOS Safari behavior of auto-zooming any focused text input whose computed `font-size` is below 16px.** The global `input, select` rule in `ui/src/styles.css` was at 15px (inherited by the chat input via `--font-text`), so focusing it triggered zoom that didn't cleanly scale back on blur — the app rendered out of bounds afterwards.

Fix considered and rejected: `<meta name="viewport" content="... maximum-scale=1, user-scalable=no">`. Would kill the zoom uniformly but also disables legitimate pinch-zoom-to-read, an accessibility regression. Bumping the input font-size to 16px is the canonical, documented way iOS Safari itself signals "this input is already large enough, no auto-zoom needed" — one-character CSS change, zero downside.

Also updated the issue title on GitHub while there: it was originally vague ("Viewport/zoom lets the app render out of bounds") without pinning the trigger; now names the actual repro path so a future look at the issue reads with the diagnosis already visible.

### What we actually built

- `ui/src/styles.css` — `input, select` font-size 15px → 16px, with a comment naming the iOS Safari mechanism so a future "why 16 not 15" question doesn't need archaeology.

Verified with a Playwright WebKit + iPhone 14 viewport that computed `font-size` on `#chat-input input` is 16px. WebKit-headless doesn't reproduce mobile Safari's auto-zoom directly (it's a mobile-Safari-only behavior), so the mechanism check is what we have here; real-device verification pending the next iOS session. Full e2e suite green (10/10).

Fix on `fix/ios-input-zoom-24` branched off `main` (independent of the still-open #22 PR since the files don't overlap). No architecture doc changes — CSS token bump only.
