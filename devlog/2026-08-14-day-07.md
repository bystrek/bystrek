# Day Seven — bystrek.dev

**Date:** 2026-08-14
**Goal:** A local dev setup script — checking prerequisites and running `api`/`ui`/Postgres locally without manual `.env` setup.

## What we decided

**`api`/`ui` run directly via `bun`, not containerized, for local dev.** Only Postgres runs in Docker (`docker-compose.dev.yml`, already existed) — fast iteration on `api`/`ui` matters more locally than parity with the deployed containers.

**Auto-generate `.env` files instead of failing when they're missing.** `ui/.env` is a trivial copy (its one var already defaults to the right local value). `api/.env` needs real VAPID keys — `api/src/env.ts` throws on startup if they're blank — generated via the `web-push` CLI's `generate-vapid-keys` (already a project dependency, pure local crypto, no external account needed).

**Seed owner name/email collected wizard-style, not left blank.** Prompts on first `api/.env` generation, defaulting to `git config user.name`/`user.email` (Enter accepts the default). Skipped entirely when stdin isn't a TTY, so a non-interactive/CI invocation doesn't hang.

**Windows: recommend WSL2 over a parallel PowerShell script.** The script needs `pgrep`-based process-tree walking for clean shutdown, which Git Bash's process model doesn't reliably support. Docker Desktop for Windows already requires WSL2 as its backend, so this isn't much of an extra ask. A duplicate PowerShell script was ruled out — ongoing maintenance burden (every future change needs a mirrored edit) for a project currently shared with one person.

## What we actually built

- `scripts/dev.sh`: checks `bun`/`docker`/docker daemon/`docker compose` are present; installs `api`/`ui` deps if `node_modules` is missing; generates `ui/.env` and `api/.env` if missing (the latter via the VAPID-keypair + seed-owner wizard above); starts dev Postgres and waits for it to be ready; runs `api` (`start:dev`) and `ui` (`dev`) concurrently. `Ctrl+C` stops both; Postgres keeps running (reused across runs, not torn down).
- `README.md`: new "Local development" section documenting the script and the WSL2 note for Windows.

## Problems hit along the way (and the actual fixes)

**First cleanup implementation relied on bash process groups (`kill -- "-$pid"` + `set -m`) and appeared completely broken — trap never fired.** Root cause turned out to be the *test method*, not the script: backgrounding the whole script itself (`./scripts/dev.sh &`) to test without blocking the terminal triggered a real bash 3.2 (macOS's system bash) quirk — SIGINT/TERM get marked "ignored upon entry" for anything launched with `&` from a non-interactive/non-job-control shell, and per bash's own docs that disposition can't be un-ignored by a `trap` inside the child, even though `trap -p` reports it as registered. Re-tested the correct way — a separate watcher process sending SIGINT to the script running in the *foreground* (the real shape of a terminal Ctrl+C) — and cleanup fired correctly. Replaced the process-group approach anyway with an explicit `pgrep -P`-based recursive tree kill, since it's portable and doesn't depend on job-control/tty state either way.

- `setsid` (tried briefly to force a new process group) doesn't exist on macOS — Linux-only (`util-linux`). Dropped once the `pgrep`-based kill made it unnecessary.
- GNU `timeout` isn't on stock macOS either; test harness had to rely on the trap's own exit instead of a hard timeout wrapper.

## Continuation: frontend framework decision (2nd session, same day)

### What we decided

**`ui` will migrate from SvelteKit to Angular (zoneless).** Started from "is Svelte worth learning if I'm not sold on it," which led to weighing React (the obvious "learn the popular one" answer) against sticking with Svelte or moving to something else.

React was ruled out first, and for a reason that turned out to matter more than any technical comparison: even the market-value argument for React (hireability) didn't apply, since the alternative outcome — getting hired to write React — wasn't wanted either. That collapsed the decision down to intrinsic fit only, no career-optionality tiebreaker.

On intrinsic fit: 12 years of professional Angular experience means dependency injection, hierarchical service scoping, and compiler-enforced separation of concerns aren't ceremony to be tolerated, they're how the work is already done well. Compared React/Vue/Svelte/Solid against that bar specifically:
- Logic-out-of-components (hooks/composables/Svelte stores) is achievable everywhere but unenforced everywhere except Angular — no compiler stops a dev from inlining logic into a component.
- Cross-tree communication (React Context, Vue `provide`/`inject`, Svelte `setContext`/`getContext`) turned out to be structurally the same hierarchical-provider mechanism as Angular's injector tree, just less formally named — not actually a gap.
- Runtime-swappable service implementations (the classic DI use case: prod vs. mock vs. staging) are also reachable via the same Context-like mechanisms, and TypeScript's structural typing sidesteps Angular's abstract-class-as-injection-token workaround.
- The one real, unresolved gap: automatic constructor-based dependency-graph resolution. Nothing outside Angular auto-wires a graph of services from declared dependencies — everywhere else, if service A depends on B, that's wired by hand. This is the piece that's genuinely Angular-only among frontend frameworks, and the piece that mattered most.

Bundle size (Angular's traditional weak spot vs. Svelte) was raised as a real counter-argument, then walked back: zoneless removes Zone.js's bundle weight and — more importantly — its runtime cost (monkey-patching every async browser API to trigger change detection), moving Angular's change-detection model close to Svelte/Solid's fine-grained signal reactivity. A baseline gap still exists (Angular's DI/template/scheduler runtime doesn't compile away the way Svelte's does), but for this app specifically — a low-traffic push-subscribe landing page with no conversion-optimization pressure — that residual gap isn't significant.

Switching cost is a non-issue either way: the current `ui` is ~237 lines total (one subscribe page, layout, service worker).
