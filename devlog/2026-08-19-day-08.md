# Day Eight — bystrek.dev

**Date:** 2026-08-19
**Goal:** Auth wiring (item 4) — the thing blocking every domain table after it.

## What we decided

**Frontend auth pieces go into SvelteKit now, not after the Angular migration.** The migration (day-07) is decided but unscoped and undated. Waiting for it would leave calendar and every other domain table blocked indefinitely on an open-ended rewrite. Backend auth is framework-agnostic either way; the frontend pieces (login form, a couple of routes) are small enough that porting them once Angular work actually starts is a fixed, bounded cost — not a reason to stall now.

**Magic-link, decided back on day six, got dropped mid-session in favor of email/password.** Started from the user's instinct that password-with-forgot-password would be simpler. Worth being honest about how that changed the plan rather than just going along with it:

- The original case against passwords (day-06: "owning hashing, reset flows, breach-list checking") overstated the real delta once we actually checked `better-auth`'s docs — it hashes passwords internally (scrypt), so the only piece actually owned is the reset flow, which magic-link would have needed anyway (its own token/link handling).
- The bigger, previously-unweighed cost of magic-link only surfaced once we got into the actual implementation: *every single login* would have required a cross-context handoff (click a link in Safari, land in the installed PWA), which is exactly the unverified iOS storage-sharing risk flagged as open in day-06. Password login happens entirely inside the already-open PWA — that risk now only touches the rare forgot-password path, not the everyday one.
- Still true, and worth keeping in view: password reuse across sites is a real residual risk hashing can't fix. Accepted here because this is a household-scale app with no public signup surface, not because the risk isn't real.

**Skip the community `nestjs-better-auth` wrapper package.** Its Bun compatibility is unconfirmed, and the project already carries one accepted Bun-compat risk (Nest-on-Bun, `architecture.md`). Mounting `better-auth`'s own handler directly (`toNodeHandler` from `better-auth/node`) and writing a five-line Nest guard avoids stacking a second unofficial-package unknown on top of the first.

**Invite reuses the forgot-password flow rather than a separate invite-token system.** An admin creates the user row, then the same Resend-backed `sendResetPassword` email goes out as "set your password." Mirrors how magic-link's `disableSignUp` used to collapse invite-acceptance and regular login into one path — same idea, different mechanism.

## What we actually built

**Schema** (`api/src/db/schema.ts`): `role`/`banned`/`banReason`/`banExpires` added to `users`; new `sessions`/`accounts`/`verifications` tables, plural-named to match the existing `households`/`users` convention (`usePlural: true` on the adapter, rather than remapping singular model names by hand).

**Backend** (`api/src/auth/`): `auth.config.ts` builds the `betterAuth()` instance as a factory taking a Drizzle `db`, wired through Nest's DI (`auth.provider.ts`, injecting the existing `DRIZZLE` token) rather than a module-level singleton with its own connection pool — matches the project's existing DI-first style and the user's own stated preference for that pattern over convenience shortcuts. `AuthGuard`/`AdminGuard` (`auth.guard.ts`) call `auth.api.getSession`; `AdminGuard` extends `AuthGuard` and adds a role check. `resend.ts` sends via a plain `fetch` to Resend's API — no SDK dependency for one email call.

`main.ts`: `bodyParser: false` on `NestFactory.create`, `better-auth`'s handler mounted at `/api/auth` ahead of a manually-added `express.json()`, since `better-auth` needs the raw body.

`HouseholdController` gained `POST /household/invite` (admin-only, inserts the row then triggers the reset-password email), `POST /household/members/:id/ban`/`unban` (admin-only, wraps the admin plugin's `banUser`/`unbanUser` — which also revokes the target's sessions immediately, real behavior worth not reinventing badly). `GET /household` is now guarded.

**Seed script**: owner row now gets `role: 'admin'`, and seeding triggers the same password-reset email so the owner gets a real password rather than none.

**Frontend** (`ui/`): no `better-auth` client library — checked its exports and found the bearer-token handling has no client-side plugin in this version, it's meant to be handled by the consuming app directly. Given the app already talks to the API via plain `fetch` everywhere else, matching that (`ui/src/lib/auth.ts`: `signIn`/`signOut`/`getSession`/`requestPasswordReset`/`resetPassword`/`authFetch`) was simpler than pulling in a client SDK for three REST calls. `+page.svelte` gained a login form, a "forgot password?" link, and — for admins — an invite form and ban/unban buttons on the household list. New route `src/routes/auth/reset-password/+page.svelte` handles both the invite and forgot-password links.

**Tests**: `AuthGuard`/`AdminGuard` unit tests (fake `Auth`/`ExecutionContext`, no DB). Integration tests sign up a real user with a real hashed password and sign in through the real endpoint (`asResponse: true` to read the bearer token off the `Response`, no HTTP mount needed) rather than faking a session — exercises the actual hashing/session/token path. `sendResetPassword`/Resend is stubbed via `mock.module` (confirmed it actually hoists ahead of other imports before trusting it, rather than assuming). Six new Playwright (WebKit) cases: signed-out shows login, signed-in member sees no admin controls, signed-in admin sees invite/ban, reset-password success and invalid-token paths.

## Problems hit along the way (and the actual fixes)

**`admin.createUser`'s `password` field: docs said required, the installed package says optional.** Fetched the public docs first and took the "required" claim onto the plan. Then checked the actual installed `1.7.1` type definitions directly (per the day-06 lesson: verify a library capability a real decision hinges on) and found `password: ZodOptional<ZodString>`. Turned out moot once the invite flow got redesigned around a plain Drizzle insert + reset-password email rather than `admin.createUser` at all — but the discrepancy itself is worth remembering: public docs can drift from the installed version; when it matters, check `node_modules`, not just the website.

**Express 5's wildcard mount syntax broke `better-auth`'s own query-string parsing.** Mounting at `/api/auth/*splat` (the pattern from `better-auth`'s own Express docs) made Express fold the *entire* matched path — including the token segment of `/reset-password/:token` — into `req.baseUrl`, leaving `req.url` as just `/` plus the query string. `better-call`'s URL-reconstruction heuristic (`baseUrl + req.url === originalUrl`) then mismatched by one slash and silently dropped the query string entirely, so `callbackURL` came through as `undefined` on every request through that route. Fix: `app.use()` already matches by path prefix on its own — drop the wildcard entirely (`app.use('/api/auth', toNodeHandler(auth))`). Found by adding a one-off debug middleware logging `req.url`/`baseUrl`/`originalUrl`, not by guessing.

**The bearer token's `set-auth-token` response header needs `Access-Control-Expose-Headers` even under Playwright's route mocking.** First pass at the e2e login test set the header directly in a mocked response and got "no session token was returned" — `ui` (port 4173) and `api` (port 3000) are different origins even inside a single Playwright browser context, so the Fetch spec's CORS header-exposure rules still apply to intercepted responses. Turned out to be a good thing to hit in a test: it's the same reason `main.ts`'s real CORS config needed `exposedHeaders: ['set-auth-token']` for production (`bystrek.dev` / `api.bystrek.dev` are genuinely cross-origin there too) — the test failure caught a requirement that was real, not a test-only artifact.

**Spent a few minutes chasing a phantom "flapping" auth bug that was just shell state.** Manually verifying the invite/ban endpoints via `curl`, a bearer token minted in one Bash tool call came back empty in a later one — each Bash invocation is a fresh shell, so `$TOKEN` set in one call doesn't survive into the next (only the working directory persists). Looked exactly like a nondeterministic session bug for a few rounds of re-testing before the actual cause clicked. No code changes; just mint and use the token within one call going forward.

**Resend rejected the actual send: `bystrek.dev` isn't a verified sending domain yet.** Caught during local end-to-end testing (403 from Resend, confirmed via the DB that the underlying token generation still worked correctly — only delivery failed). Flagged, not fixed here — needs the user to add SPF/DKIM records for `bystrek.dev` in Resend's dashboard before real emails go out; local testing worked around it by pulling the reset token directly from the `verifications` table.

**Local dev Postgres got polluted by manual testing again** — same class of issue as day six. Seeded rows and a leftover invited test member briefly made `household-endpoint.integration.spec.ts`'s "oldest household" assertion fail against real committed rows outside the test's rolled-back transaction. Cleared them and reran clean; not a code bug.

## Continuation: landing it — CI, deploy, prod seeding, real-device test (2nd session, same day)

**Goal:** Get the branch through CI, deployed, and settle the one open question (iOS storage sharing) on a real device.

### What we decided

Nothing new decided — this was landing/verification work on the plan above, not a design session.

### What we actually built/verified

- PR #3 (`auth-wiring` → `main`) merged after fixing a CI gap: `env.ts` reads `AUTH_SECRET`/`RESEND_API_KEY` at module load via `required()`, and `auth.guard.spec.ts` transitively imports that chain, so `test-api` needed throwaway values for both in `deploy.yml` — same pattern already used there for the VAPID keys. One extra commit, CI green after.
- Deploy ran clean end to end: build → gated `production` environment approval → SSH deploy. Verified live (`GET /household` 401s without a token, `/api/auth/get-session` responds).
- Ran `db:seed` on the droplet — no output, which turned out to be correct rather than broken: the household/owner row already existed from day six, before `better-auth` existed, so the `if (!existing)` guard skipped both the insert and the new password-reset trigger. Checked directly (`psql` over SSH): `role` was `user` (from the migration's column default, not the seed script's `'admin'`), and `accounts` had zero rows — the owner had no password at all yet. Fixed with a one-off `UPDATE users SET role = 'admin'` plus a manual `POST /api/auth/request-password-reset` call (the same endpoint `sendResetPassword` uses) to create the missing `accounts` row. The SQL update got blocked by Auto Mode's Bash classifier (same class of block as `git push` on day six) — user ran it directly.
- Real Resend send confirmed once the user verified `bystrek.dev` in Resend's dashboard: the local 403 (unverified domain) from earlier in the day went away, a real email arrived.
- **Real-device check done, the one open question from day six carried all the way through to today**: Safari and the installed PWA do *not* share `localStorage` on iOS. Confirmed, not assumed. Turned out to be a non-issue given how the reset flow was actually built: `resetPassword` deliberately never establishes a session, only changes the password — there was never a token meant to cross from Safari into the PWA. The fallback (open the PWA separately, sign in fresh with the new password) was the intended path all along, not a patch applied after finding out storage isn't shared.

### Problems hit along the way (and the actual fixes)

- **A CI run took ~8 minutes instead of the usual ~1.** Not a regression — `~/.cache/ms-playwright`'s cache key (hashed from `ui/bun.lock`) was byte-identical to the last successful run's, confirmed by diffing both logs directly, but GitHub Actions evicts cache entries after 7 days of no access and it had been 11 days since the last CI run on this repo. Nothing to fix; next run repopulates it.
- **The `production` deploy gate appeared to skip the required-reviewer pause** — deploy started 46 seconds after `build-ui` finished with no visible wait in the log. Flagged it rather than assuming a misconfiguration; turned out the user had just approved it quickly. Environment protection is working as documented.
