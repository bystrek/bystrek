# Day Eleven — bystrek.dev

**Date:** 2026-08-22
**Goal:** Ship the chat page — the last piece of item 5 in `whats-next.md` — plus a small user profile page (name + avatar) added to today's scope. Wire a routed `/chat` page in `ui` to the already-live `POST /chat` SSE backend, streaming Claude's reply into a message list; add a `/profile` page for editing first/last name and an avatar.

## What we decided

**Profile: reuse `better-auth`'s own `update-user` endpoint and `image` field, don't hand-roll a controller.** Original ask was a new `users` column (base64 picture) + a new custom update endpoint + a UI page. Checked the actually-installed `better-auth` (v1.7.1) first: `image` is already a core field its built-in `POST /api/auth/update-user` endpoint accepts and writes straight to the user row (we just don't have the column yet), and `user.additionalFields` in `auth.config.ts` is the declared way to add more self-editable columns (`firstName`/`lastName`) — once declared, the same endpoint accepts them in the same batched call, and `get-session` returns them automatically, no new GET endpoint needed either. So the only new backend work is three nullable `users` columns (`image`, `first_name`, `last_name`) and an `additionalFields` declaration — no `ProfileController`, no new module. Same reasoning as picking Caddy over nginx on day 10: reuse a tool already fully wired into this stack over hand-rolling the standard-shaped equivalent. Storage stays plain `text` (a data-URI string), not `bytea` — going through better-auth's generic field path means it has to be a string type regardless, and a profile photo is the same sensitivity class as the already-plaintext `name`/`email` columns, so tier-2 field encryption doesn't apply here.

**Avatar gets downscaled/re-encoded client-side before it's sent.** A raw phone photo can be several MB; canvas-resize to a small square (~256px) and re-encode as JPEG before base64-encoding, so a typical upload stays a few tens of KB rather than blowing up the request body and the DB row. `name` (the existing single-field core column, read elsewhere for "Signed in as…") gets recomputed as `` `${firstName} ${lastName}`.trim() `` and sent in the same batched `update-user` call, so it never drifts out of sync with the new split fields.

**`name` is derived one-way from `firstName`/`lastName`, never the other way around.** First pass considered splitting the existing `name` value back into two inputs for editing (naive whitespace split) to avoid adding new columns at all — rejected once raised: a single-field split doesn't round-trip for anyone with multiple first or last names, so the canonical editable source has to be `firstName`/`lastName` themselves, with `name` as a pure write-side derivation kept in sync on every save. The only wrinkle: a user's very first profile visit shows blank first/last name inputs even though `name` already has a value from invite/seed — acceptable for a household this size, and both fields are required before submit so nothing gets silently blanked out.

**Add `GET /chat/history` today, not defer it.** The backend only exposes `POST /chat` right now — there's no way to load prior turns. The whole reason `messages` is a single continuous thread (not per-conversation, see day 9) was so history persists across sessions; a chat page that goes blank on every refresh undercuts that. The addition is small — reuse `ChatService.loadRecentMessages`'s existing decrypt path, collapse each row to plain text, drop turns that are pure `tool_use`/`tool_result` (no tool-result rendering exists yet, matches the "text only for v1" decision from day 9).

**Split into 4 PRs, each its own session — not chained through in one sitting.** Backend/frontend split per feature, mirroring how this repo already shipped chat's backend (#4) and the Angular rewrite (#5) as separate PRs: PR1 profile-backend → PR2 profile-frontend (depends on PR1), PR3 chat-backend → PR4 chat-frontend (depends on PR3). Each PR gets picked up cold in a fresh session — this devlog entry is the plan each of those sessions works from; a "What we actually built" writeup gets appended per PR as it lands, not all at once. Docs close out afterward as direct-to-main commits (no PR), matching how day 10 closed out (`932338b`).

**Scope:** `users` table gains `image`, `first_name`, `last_name` (all nullable `text`); `auth.config.ts` declares the two new fields as `additionalFields`.

  },

## Continuation: formatting unification (2nd session, same day)

### What we decided

**PR1 (profile backend) work got stashed mid-session to fix a tooling gap first.** While sanity-checking PR1 with `bun run lint` (api's script bundles `eslint --fix`), the autofix reformatted three unrelated files (`auth.guard.spec.ts`, `household.controller.ts`, `test/integration/support/auth.ts`) that weren't already prettier-clean on `main`. That's a symptom of a real gap, not a one-off: `api` has prettier wired through `eslint-plugin-prettier` but nothing ever runs it automatically (no pre-commit hook, no CI step) — it only fires when someone happens to run `bun run lint`. `ui` has prettier installed (Angular CLI's default scaffolding) but literally nothing invokes it — no `format` script, no eslint at all. Decided to fix this now rather than let it keep silently corrupting unrelated diffs in future sessions. PR1's changes (schema/auth-config/migration/integration test) are intact in `git stash@{0}`, untouched by this work.

**One root `.prettierrc`, not two per-project ones.** `api/.prettierrc` (`singleQuote`, `trailingComma: all`) and `ui/.prettierrc` (`singleQuote`, `printWidth: 100`, an `angular` parser override for `*.html`) already agreed on `singleQuote` but diverged on `printWidth`/`trailingComma` for no real reason — neither project's code style demands a difference. Deleting both in favor of one root config Prettier resolves by walking up from each file (no monorepo/workspace tooling needed, this isn't a workspace repo) gives one answer to "how is this file formatted" regardless of which project it's in. Kept the `*.html` → `angular` parser override in the shared config; it's a no-op for `api`, which has no `.html` files.

**Checked Biome, dprint, and oxfmt (oxc project) before committing to Prettier — none of them work for this repo today.** Biome's HTML support is experimental and disabled by default; Angular's control-flow syntax (`@if`/`@for`/`@defer`) isn't formatted yet (open issue). dprint's Angular support is a third-party plugin (`markup_fmt`, not from dprint or Angular) with undocumented file-detection behavior — not confidence-inspiring. oxfmt is the real contender: 100% Prettier JS/TS conformance claimed, explicit Angular template/style support, ~30x faster, already adopted by Vue.js and Turborepo — but it detects Angular templates by filename, only treating `*.component.html` as Angular. Our templates (`app.html`, `main.html`, `login.html`, `reset-password.html`) follow the newer Angular CLI convention that dropped the `.component.` suffix, so oxfmt would parse them as plain HTML and mangle Angular syntax. Its own compatibility table flags this ("`.html` requires config override") but the override doesn't exist yet — tracked in `oxc-project/oxc#17852`, open, unassigned, no PR. Revisit oxfmt once that issue ships; Prettier is the only one of the three with confirmed working Angular support that matches how this project actually names its files.

**CI format:check blocks the pipeline, not just reports.** Chose to fail `test-api`/`test-ui` on a formatting violation (same severity as a failing test) rather than a non-blocking report step. The alternative (report-only, grace period) risks exactly the kind of silent drift that caused this detour in the first place, and the fix is always a single `prettier --write` away — low friction to require it up front.

**Enforced via existing CI jobs, not a new pre-commit hook.** `test-api`/`test-ui` already run on every push/PR; adding a `format:check` step there reuses infrastructure that's already gating merges (per the day-10 "reuse a tool already in the stack" reasoning). No `husky`/`lint-staged` — nothing in this repo uses git hooks today, and CI is already the enforcement point for tests, so it's the enforcement point for formatting too.

### What we actually built

One root `.prettierrc` (`singleQuote`, `trailingComma: all`, `printWidth: 100`, `*.html` → `angular` parser override), replacing `api/.prettierrc` and `ui/.prettierrc`. Added `format`/`format:check` scripts to `ui/package.json` (it had neither before) and a `format:check` script to `api/package.json` (it already had `format`, which now also covers root-level `.ts` files like `drizzle.config.ts`). Reformatted both codebases under the unified config — pure whitespace/line-wrap changes throughout, spot-checked several diffs by hand to confirm nothing semantic moved. Added a `bun run format:check` step to both `test-api` and `test-ui` jobs in `.github/workflows/deploy.yml`, ahead of the existing test steps, so a misformatted file fails CI the same as a failing test.

### Problems hit along the way (and the actual fixes)

`bun run lint` in `api` bundles `eslint --fix` — running it (twice, once before and once after an interleaved `git stash`, while sanity-checking the formatting change) auto-fixed three unrelated files (`auth.guard.spec.ts`, `household.controller.ts`, `test/integration/support/auth.ts`) that weren't prettier-clean on `main` yet. This is what triggered the whole detour in the first place. Recovered by diffing the stash against `HEAD` (`git diff HEAD stash@{0} --stat`) to see exactly which files it touched, `git checkout --` the stray ones back to `HEAD`, and `git checkout stash@{0} -- <files>` to pull just PR1's real changes back into the working tree, then re-stashed PR1's work as one clean labeled entry (`git stash push -u -m "PR1 profile-backend: ..."`) before starting this PR. Ran into it a second time mid-verification — `bun run lint` silently reintroduced an unrelated fix (`(await x()) as Response` → `await x()`, an eslint `no-unnecessary-type-assertion` autofix, not a prettier formatting decision) into `support/auth.ts`. Caught it by re-running a bare `bunx prettier --write` on that file, which reported it "unchanged," proving the earlier diff wasn't formatting at all; reverted it and re-ran a full idempotent `prettier --write` pass across `api` (all files reported "unchanged") to confirm nothing else had been silently mixed in. Takeaway: don't run `bun run lint` (or any `--fix`-bundled script) as a "just checking" step on someone else's/older files — its autofix isn't scoped to intent, only to whatever's on disk. Verifying eslint's prettier integration should have been a plain `prettier --check`/`format:check`, not the fix-on-write lint script.

Also evaluated Biome, dprint, and oxfmt as faster alternatives before committing to Prettier (prompted by a direct question, not part of the original plan) — see "What we decided" above for why all three lose to Prettier today, specifically because this project's Angular templates (`app.html`, not `*.component.html`) hit an open, unfixed oxfmt bug.

`ui/node_modules` had never been installed in this environment — `bun install` was needed before `format:check`/`build`/`test` would run at all.
