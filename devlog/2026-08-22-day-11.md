# Day Eleven — bystrek.dev

**Date:** 2026-08-22
**Goal:** Ship the chat page — the last piece of item 5 in `whats-next.md` — plus a small user profile page (name + avatar) added to today's scope. Wire a routed `/chat` page in `ui` to the already-live `POST /chat` SSE backend, streaming Claude's reply into a message list; add a `/profile` page for editing first/last name and an avatar.

## What we decided

**Profile: reuse `better-auth`'s own `update-user` endpoint and `image` field, don't hand-roll a controller.** Original ask was a new `users` column (base64 picture) + a new custom update endpoint + a UI page. Checked the actually-installed `better-auth` (v1.7.1) first: `image` is already a core field its built-in `POST /api/auth/update-user` endpoint accepts and writes straight to the user row (we just don't have the column yet), and `user.additionalFields` in `auth.config.ts` is the declared way to add more self-editable columns (`firstName`/`lastName`) — once declared, the same endpoint accepts them in the same batched call, and `get-session` returns them automatically, no new GET endpoint needed either. So the only new backend work is three nullable `users` columns (`image`, `first_name`, `last_name`) and an `additionalFields` declaration — no `ProfileController`, no new module. Same reasoning as picking Caddy over nginx on day 10: reuse a tool already fully wired into this stack over hand-rolling the standard-shaped equivalent. Storage stays plain `text` (a data-URI string), not `bytea` — going through better-auth's generic field path means it has to be a string type regardless, and a profile photo is the same sensitivity class as the already-plaintext `name`/`email` columns, so tier-2 field encryption doesn't apply here.

**Avatar gets downscaled/re-encoded client-side before it's sent.** A raw phone photo can be several MB; canvas-resize to a small square (~256px) and re-encode as JPEG before base64-encoding, so a typical upload stays a few tens of KB rather than blowing up the request body and the DB row. `name` (the existing single-field core column, read elsewhere for "Signed in as…") gets recomputed as `` `${firstName} ${lastName}`.trim() `` and sent in the same batched `update-user` call, so it never drifts out of sync with the new split fields.

**`name` is derived one-way from `firstName`/`lastName`, never the other way around.** First pass considered splitting the existing `name` value back into two inputs for editing (naive whitespace split) to avoid adding new columns at all — rejected once raised: a single-field split doesn't round-trip for anyone with multiple first or last names, so the canonical editable source has to be `firstName`/`lastName` themselves, with `name` as a pure write-side derivation kept in sync on every save. The only wrinkle: a user's very first profile visit shows blank first/last name inputs even though `name` already has a value from invite/seed — acceptable for a household this size, and both fields are required before submit so nothing gets silently blanked out.

**Add `GET /chat/history` today, not defer it.** The backend only exposes `POST /chat` right now — there's no way to load prior turns. The whole reason `messages` is a single continuous thread (not per-conversation, see day 9) was so history persists across sessions; a chat page that goes blank on every refresh undercuts that. The addition is small — reuse `ChatService.loadRecentMessages`'s existing decrypt path, collapse each row to plain text, drop turns that are pure `tool_use`/`tool_result` (no tool-result rendering exists yet, matches the "text only for v1" decision from day 9).

**Split into 4 PRs, each its own session — not chained through in one sitting.** Backend/frontend split per feature, mirroring how this repo already shipped chat's backend (#4) and the Angular rewrite (#5) as separate PRs: PR1 profile-backend → PR2 profile-frontend (depends on PR1), PR3 chat-backend → PR4 chat-frontend (depends on PR3). Each PR gets picked up cold in a fresh session — this devlog entry is the plan each of those sessions works from; a "What we actually built" writeup gets appended per PR as it lands, not all at once. Docs close out afterward as direct-to-main commits (no PR), matching how day 10 closed out (`932338b`).

## Plan

### PR1 — Profile: backend

**Scope:** `users` table gains `image`, `first_name`, `last_name` (all nullable `text`); `auth.config.ts` declares the two new fields as `additionalFields`.

**Files:**
- `api/src/db/schema.ts` — add the three columns to the `users` table definition (`image` is a bare column, no special handling — better-auth treats it as core).
- `api/drizzle/` — `bun run db:generate` for the migration, `bun run db:migrate` to apply locally.
- `api/src/auth/auth.config.ts` — add:
  ```ts
  user: {
    additionalFields: {
      firstName: { type: 'string', required: false, input: true },
      lastName: { type: 'string', required: false, input: true },
    },
  },
  ```
- No new controller/module — `POST /api/auth/update-user` and `GET /api/auth/get-session` are already mounted (better-auth is mounted wholesale) and already bearer-gated by better-auth's own session middleware.

**Tests:** new `api/test/integration/profile.integration.spec.ts`, following the `withRollback` + `testDb` + `signUpTestUser` pattern used in `household-endpoint.integration.spec.ts`. No existing test hits a better-auth core route over HTTP (all existing supertest calls target this app's own controllers; `signUpTestUser` calls better-auth in-process), so this test issues a real `supertest` request against `/api/auth/update-user` with the test user's bearer token, then asserts `{ firstName, lastName, image, name }` round-trip through `GET /api/auth/get-session`.

**Verification:** `bun test src` and `bun test test/integration` both green; manual curl against `/api/auth/update-user` with a real bearer token as a sanity check before writing the automated test.

### PR2 — Profile: frontend

**Depends on PR1 merged** (needs the columns/fields to exist against a running local `api`).

**Scope:** a `/profile` page — first/last name inputs + a file input for the avatar — wired to better-auth's `update-user`/`get-session` endpoints directly via `AuthService` (no separate profile service needed, matching how `AuthService` already calls other better-auth endpoints directly).

**Files:**
- `ui/src/app/core/auth/auth.service.ts` — widen `Session['user']` to include `firstName`, `lastName`, `image` (nullable strings); add `updateProfile(firstName, lastName, image)` that POSTs `{ name: \`${firstName} ${lastName}\`.trim(), firstName, lastName, image }` to `${environment.apiUrl}/api/auth/update-user`, then re-runs `initSession()` to refresh the displayed session (`update-user` only returns `{ status: true }`).
- `ui/src/app/features/profile/` (new): `profile.ts`/`.html`/`.css`. Form fields as signals (matching `main.ts`'s `inviteName`/`inviteEmail` pattern); first/last name both `required` (matches the invite form, prevents an accidental blank overwrite of `name` before either field has ever been set). File input's `change` handler draws the picked image to an off-screen `<canvas>`, downscales to a small square (~256px), and calls `toDataURL('image/jpeg', 0.8)` for the base64 payload.
- `ui/src/app/app.routes.ts` — add `/profile` (`authGuard`, lazy-loaded like the others).
- `ui/src/app/features/main/main.html` — link to `/profile`.

**Tests:**
- `auth.service.spec.ts` — extend with cases for `updateProfile`, following its existing `HttpTestingController` pattern.
- A unit test for the canvas-downscale helper if extracted as a standalone function.
- `ui/e2e/profile.spec.ts` (new) — fill first/last name, attach a small fixture image, submit, assert the `update-user` request body and that the displayed name/avatar refresh. Mock the HTTP call via `route.fulfill`, matching how `subscribe.spec.ts`/`household.spec.ts` already mock their backend calls.

**Verification:** `bun run build`, `bun run test`, `bun run test:e2e` all green; manual click-through in a browser against the real local `api` from PR1 to confirm the avatar round-trips and downscaling actually shrinks a real phone-sized photo.

### PR3 — Chat: backend (`GET /chat/history`)

**Scope:** expose the persisted thread as a plain-text list for the frontend to load on open.

**Files:**
- `api/src/chat/chat.service.ts` — extract a pure function that collapses decrypted `MessageParam[]` rows into `{ role, text }[]`: concatenates `text`-type content blocks per turn, drops any turn with no resulting text (pure `tool_use`/`tool_result` turns — no per-tool rendering exists yet, matches the "text only for v1" call from day 9).
- `api/src/chat/chat.controller.ts` — add `@Get()` handler, `@UseGuards(AuthGuard)`, reuses the existing `loadRecentMessages` decrypt/window logic, feeding its output through the new collapse function.

**Tests:** unit test the collapse function directly under `api/src/chat/` (co-located `*.spec.ts`, pure logic, no DB) — cases: plain text turn, tool_use-only turn (dropped), mixed content, empty history. Optionally extend `chat.integration.spec.ts` with one case hitting the new `GET` route end-to-end.

**Verification:** `bun test src` and `bun test test/integration` green; manual curl against a real seeded thread to eyeball the response shape.

### PR4 — Chat: frontend

**Depends on PR3 merged.**

**Scope:** the chat page itself — message list, input, SSE streaming via `HttpClient`.

**Files:**
- `ui/src/app/core/chat/chat.service.ts` (new): signals `messages`, `sending`, `error` (same shape as `PushService`/`HouseholdService`). `loadHistory()` calls `GET /chat/history` on page load. `send(text)` posts to `POST /chat` via `HttpClient` with `observe: 'events'`, `responseType: 'text'`, `reportProgress: true` — the XHR backend (`withXhr()`, already configured) exposes growing `partialText` on `DownloadProgress` events, so SSE deltas can be read incrementally without a raw `fetch()`. Parse complete `data: {...}\n\n` frames out of the accumulated text as they arrive; append each `delta` to the trailing assistant message. Outgoing sends route through a `Subject` + `switchMap` (per the architecture doc's stated reason for RxJS here) to cancel an in-flight stream if superseded, even though the UI also disables input while `sending()` is true.
- `ui/src/app/features/chat/` (new): message list (user/assistant bubbles), auto-scroll on new content, input + send button disabled while `sending()`. Loads history in `ngOnInit`.
- `ui/src/app/app.routes.ts` — add `/chat` (`authGuard`, lazy-loaded).
- `ui/src/app/features/main/main.html` — replace the "Chat is offline for now" placeholder with a real link to `/chat`.

**Tests:**
- Vitest for `ChatService` via `HttpTestingController`, simulating staged `DownloadProgress` events with growing `partialText` plus a final `Response` — same pattern as `auth.service.spec.ts`.
- `ui/e2e/chat.spec.ts` (new) — mock `GET /chat/history` (empty) and `POST /chat` (small fake SSE body via `route.fulfill`), assert: typed message appears, streamed reply renders, input/button disabled mid-stream and re-enabled after.

**Verification:** `bun run build`, `bun run test`, `bun run test:e2e` all green; manual click-through against the real local `api` (real Anthropic call) to confirm actual streaming renders correctly, not just the mocked e2e path.
