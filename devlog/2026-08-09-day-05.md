# Day Five — bystrek.dev

**Date:** 2026-08-09
**Goal:** Step back and assess how the project's been run so far, close out day four's loose ends for a clean slate, and decide a testing strategy before starting the next feature (calendar).

## What we decided

**Retrospective: scope/pace is the real risk, not any individual decision.** Asked for an honest assessment of the working style across days one through four. The good parts held up under scrutiny: verify-before-trust discipline (smoke tests, confirming migrated data before deleting it, checking Open WebUI's subpath bug reports before risking a change), real prose discussion before big irreversible picks (already captured as a standing preference), and catching doc drift (the `architecture.md`-as-transcript fix on day four). The flagged risk: four sessions in, infra/stack surface area has grown a lot faster than shipped product — no vertical slice (calendar, chat) exists yet. Agreed this is the thing to actively watch going forward, not any single technical call made so far.

**Cloudflare token: no action needed.** Checked the dashboard directly rather than assuming — it's a scoped `API Token` (`Zone.DNS`, one zone), not the legacy account-wide Global API Key. A leak of it can only edit DNS on `bystrek.dev`, nothing else. Loose end closed by inspection, not by changing anything.

**Backup strategy: local-only daily `pg_dump`, no off-droplet copy, no encryption at rest.** Rejected DigitalOcean's managed droplet backups outright (extra recurring cost not justified for a hobby project) and rejected encrypting the dump file. Reasoning for skipping encryption, given twice: if the droplet itself is ever compromised, an unencrypted local dump doesn't add meaningful incremental exposure over what's already lost; and once tier-2 field encryption (already decided in `architecture.md`) is actually wired into the schema, sensitive columns are ciphertext at the app layer before they ever reach `pg_dump`, so the backup file wouldn't contain plaintext medical data regardless. Explicitly named and accepted gap: this protects against bad migrations and accidental deletes, not against losing the droplet entirely — revisit if that stops being an acceptable risk.

**Testing strategy, decided layer by layer:**
- **Backend runner: switch from Nest's default Jest scaffold to Bun's native `bun:test`.** Tempting specifically because it's consistent with the project's existing Bun-native bet (Drizzle), but flagged as stacking a second unverified Bun/Nest combination on top of the residual Nest-on-Bun risk already accepted on day four. Decided to try it anyway — reasoning explicitly given: this isn't an enterprise project with a large team to protect, the fallback (Jest, on Node) is cheap and already documented, so the downside of trying and reverting is small. A quick spike confirming `@nestjs/testing`'s `TestingModule` actually runs under `bun:test` should happen before ripping out the Jest scaffold, same "verify before trust" instinct as everywhere else.
- **Backend test emphasis: integration over mocked unit tests.** Given Drizzle was chosen specifically to stay close to real SQL instead of hiding it behind an ORM, and given tier-2 encryption is coming, the tests that actually catch real bugs here are ones that hit a real Postgres — not a mocked DB layer. Plan: each integration test wrapped in a transaction that gets rolled back afterward, so tests can't leak state into each other and there's no re-migrate/re-seed cost between them. Unit tests reserved for genuinely pure logic (encryption helpers, tool-call-loop parsing).
- **Frontend: Vitest for unit/component logic, Playwright for e2e.** Checked whether Playwright still deserved the pick rather than assuming — compared against Cypress and Selenium. Two concrete, project-specific reasons it won: Playwright bundles a real WebKit engine (the actual target here is iOS Safari fidelity, not generic cross-browser coverage — Cypress has no WebKit, Selenium only gets real Safari via a device farm), and Playwright has a virtual WebAuthn authenticator via CDP, which maps directly onto the passkey login flow already decided in `architecture.md`. Also the officially-recommended e2e tool in SvelteKit's own docs/scaffolding, same "prefer the well-trodden combination" reasoning already applied to Drizzle/NestJS.
- **E2E scope kept deliberately small** — a handful of real user journeys (subscribe-to-push, passkey login, one calendar happy path), not exhaustive edge-case coverage, which belongs in cheaper unit/integration tests instead.
- **Flakiness and the 10-minute CI budget addressed as the same problem**, not separately: the two things that actually make e2e/integration suites flaky (shared DB state between tests, real calls to third parties like Resend/CalDAV/FCM) are also the two things that make them slow. Fixing both means: transaction-rollback isolation (above), stubbing every third-party call at the boundary in every test, WebKit-only in CI (skip Chromium/Firefox — nothing here depends on them), caching the Playwright browser binary, running Postgres as a GitHub Actions service container, and an explicit `timeout-minutes: 10` on the CI job so a budget regression fails loudly instead of drifting.
- **CI gate:** both `api.yml` and `ui.yml` currently build and push to GHCR with zero test step in between — agreed to add a test step before the Docker build/push in both, no pushback needed on this one.

- **Built and deployed the backup mechanism**: `infra/backup/pg-backup.sh` (dumps via `docker compose exec postgres pg_dump`, gzips to `/root/bystrek-backups/` — deliberately outside `~/bystrek/` so wiping the stack directory can't also wipe backups, 14-day retention via `find -mtime -delete`) plus `pg-backup.service`/`pg-backup.timer` (systemd, daily, `Persistent=true` so a missed run catches up after downtime). Checked into `infra/backup/`, following the same manually-synced pattern already used for the Caddyfile/compose file. Deployed via `scp`, ran one dump manually and verified it (gzip integrity check passed, `zcat` confirmed real `pg_dump` SQL content) before trusting the timer, then enabled it.
- **Docs updated to match**: `infra/README.md` documents the backup mechanism and its accepted gaps; `docs/whats-next.md`'s loose-ends section closed out and a new "Testing infra" item added as the explicit next punch-list entry (before calendar); `docs/architecture.md`'s testing question moved from "open" to a decided section, and a second stale open question (Open WebUI retire-or-keep) removed since it was already resolved days ago and contradicted `CLAUDE.md`'s own current-state note.

## Testing infra: built and verified, same session

There ended up being enough time to build the testing infra too, not just plan it — so it shipped today rather than waiting for a future session.

- **`api`**: dropped Jest entirely (`jest`, `ts-jest`, `@types/jest`, and the now-unused `ts-node` removed; `test/jest-e2e.json` deleted). `bun test` confirmed working against the existing `@nestjs/testing`-based spec with zero code changes needed — the only real compatibility finding was that Nest's `*.e2e-spec.ts` naming convention doesn't match Bun's default test glob (`*.spec.ts`/`*.test.ts`), so the new integration tests use `*.integration.spec.ts` instead. Built `test/integration/support/rollback.ts` (wraps a test in a Postgres transaction, forces a rollback via a sentinel error afterward) and `test/integration/support/test-db.ts`, then wrote a real integration test for `POST /push/subscribe` that overrides the `DRIZZLE` provider with the transaction-scoped client so the whole Nest app runs inside it.
- **`ui`**: added Playwright, WebKit only (`bunx playwright install webkit`). The subscribe-flow e2e test stubs the browser's Push API surface (`navigator.serviceWorker`, `Notification`, `PushManager`) via `page.addInitScript` and stubs the two backend calls via `page.route()` — deliberately not exercising a real push subscription, since that needs a real push service and is already verified manually against the deployed stack (day three/four). Runs in ~0.4s per test.
- **CI**: both `api.yml` and `ui.yml` got a `test` job gating the existing `build-and-push` job via `needs:`. `api`'s test job runs a real `postgres:16-alpine` service container, `drizzle-kit migrate`, then unit + integration tests, using a throwaway (but validly-shaped) VAPID keypair generated just for CI — never used for real push delivery. `ui`'s test job caches the Playwright WebKit binary via `actions/cache`. Both jobs carry `timeout-minutes: 10`.

## Problems hit along the way (and the actual fixes)

- **The first integration test run failed** — `toHaveLength(1)` got `2`, `toHaveLength(0)` got `1`. Not a bug in the rollback: the local dev Postgres already had real subscription rows in it from manual testing across days three/four, so querying "all rows in the table" was always going to be wrong regardless of isolation working correctly. Fixed by scoping every assertion to the specific endpoint the test itself created (`where(eq(subscriptions.endpoint, ...))`), which is also just the more correct pattern for asserting against a real database. Confirmed the rollback genuinely leaves no trace by running the suite twice and querying Postgres directly afterward for leftover rows — none.
- **The WebKit e2e test's first run failed** with "The string contains invalid characters" — the fake VAPID public key stubbed into the response (`'fake-vapid-public-key'`) isn't valid base64url, and the app's own `urlBase64ToUint8Array` feeds it straight to `atob()`. Fixed by generating an actually-valid base64url string (doesn't need to be a real EC key, just decodable) instead of an arbitrary placeholder.
- **Simulated the exact CI recipe locally before trusting it**, same "verify before trust" instinct as the rest of the project: a scratch `postgres:16-alpine` container on a throwaway port, fresh (no prior migrations), ran `db:migrate` → unit → integration against it end to end before writing a single line of the actual GitHub Actions YAML.
- Running `bun run lint --fix` while checking the new integration spec reformatted three unrelated pre-existing files (`schema.ts`, `push.controller.ts`, `push.service.ts`) — pure Prettier line-wrapping the project's own config had never been run against, no logic changes (diffed to confirm before committing).

## Continuation: deployment model (second session, same day)

**Goal:** Reconsider the deploy pipeline. The Watchtower-poll / Dockge-manual-click model has real lag and doesn't match what's actually wanted: infra-as-code, where the droplet's state originates from the repo, not from manual changes on the box that get documented (or scp'd back) after the fact.

### What we decided

**Watchtower is archived upstream, not just rumored to be.** Checked rather than trusting the claim secondhand: `containrrr/watchtower` went read-only on 2025-12-17, maintainers said they no longer use Docker themselves. `nicholas-fedor/watchtower` is the actively-maintained fork, fully config-compatible (same env vars, just a different image name) — a mechanical swap, not a redesign. Not yet applied to `infra/` or the droplet; queued as a follow-up.

**Infra-as-code and "who triggers the deploy" are two separate decisions, and conflating them was slowing this down.** The repo currently only mirrors the droplet's config after the fact (`infra/` is documented as manually scp'd), which is backwards from IaC — the droplet should be *derived from* the repo, not the other way round. Decided on Ansible as the apply mechanism (standard fit for "keep one VM's docker-compose state in sync with a repo," templated and idempotent) over heavier alternatives: a GitOps tool like Komodo was rejected as solving a fleet-management problem this project doesn't have and adding another always-on service to trust; Terraform/OpenTofu was set aside as a different layer (provisioning the droplet/DNS itself, not what runs inside it). Crucially, decided to run the playbook by hand for now, using the SSH key that already has full access — that gets the actual thing wanted (repo is truth, no more manual droplet edits) immediately, with zero new secrets or exposure anywhere, and defers "should CI get a deploy credential" as a genuinely separate, lower-urgency question.

**On CI eventually getting SSH access, if it does:** a "non-root deploy user" alone was rejected as a meaningful boundary — that user still needs `docker` group membership to run compose, and docker-group membership is root-equivalent (trivial to mount `/` from the host and get a real root shell). The actual mitigation, if/when this is revisited, is restricting the credential itself: a forced command in `authorized_keys` (or `rrsync`-style restriction for file sync), scoped to only the specific deploy command, `no-pty`/`no-port-forwarding`/etc. Not built yet — parked until CI-triggered deploy is actually wanted.

**Dev/prod split: wanted eventually, explicitly deferred.** The shape, when it happens: dev auto-deploys on every push to `main`, prod deploys only on a tagged release and requires a manual gate — recognized as a natural fit for GitHub Actions' native `environment` protection rules (separate secrets per environment, required-reviewer approval before the prod job runs), not something to hand-roll. Deliberately not building this now — no real features exist yet to protect, so the split would be speculative infra ahead of need. Decided: shared droplet (not a second droplet) when the split does happen, accepting reduced isolation for cost/ops simplicity now, revisit once real user data (tier-2 encrypted fields, per `architecture.md`) is actually live. Also clarified: `bystrek.dev` doesn't "become" prod later, it already is prod's real address — the only new thing at split time is a second stack and a subdomain for dev, which is the CT-log/identity tradeoff `CLAUDE.md` already flags, to be surfaced again when that day comes, not now.

**Watchtower's fate once Ansible/CI-driven deploys exist: remove it, don't keep it as a safety net.** Reasoning: it would just be a second, slower path doing the same job (pull + redeploy) as the CI-triggered one, and it's not a free safety net — it's a standing, always-on service with read-write Docker socket access (root-equivalent, network-reaching) sitting on the box permanently. If the CI-driven path is trusted, that's attack surface bought for nothing; better to make that path reliable (retries, failure alerting) than paper over its gaps with a background poller. Sequencing decided explicitly: prove the Ansible deploy path first, remove Watchtower after, not in the same step — so there's never a gap with no fallback at all. Dockge is unaffected by this reasoning (it's a manual button, not an auto-updater) and stays a separate question.

No code or infra changed this session — planning only. Concrete follow-ups now queued, not yet built: swap the Watchtower image, write the first Ansible playbook for the single current environment (no dev/prod scaffolding yet — that's still speculative), and only revisit CI deploy credentials once that's proven out by hand.

## Continuation: CI-triggered deploy, built (third session, same day)

**Goal:** Come back to the deploy-model discussion and actually build it — but first re-examine whether Ansible was really the right call, since the earlier comparison against Komodo/Terraform hadn't been discussed in real depth (feedback from the previous session, resurfacing a standing preference: architecture decisions need genuine tradeoff discussion, not just a decision recorded from a thin comparison).

### What we decided

**Found a stale doc claim while re-checking the Watchtower situation.** `infra/dockge-docker-compose.yml` already runs `nickfedor/watchtower` — the fork — even though `whats-next.md` still listed "swap to the fork" as a not-yet-built follow-up. Git history on that file shows only one commit, predating this session, so the swap happened at some earlier, undocumented point and the punch list just never caught up. Corrected as part of this session's doc pass, not treated as a new task.

**Real comparison this time: Ansible vs. Kamal vs. Komodo vs. Docker Swarm vs. a plain script**, researched fresh rather than assumed. Ansible: mature, agentless, general-purpose config management — but using it just to sync one compose file and a Caddyfile only exercises a sliver of what it's for, plus real ceremony (inventory, playbook structure) for what's currently one host. Kamal (37signals): purpose-built for exactly "deploy a dockerized app to a VPS over SSH," zero-overhead, proven at real scale (they run HEY on it) — but its `kamal-proxy` wants to own reverse-proxy/TLS, which conflicts with the Caddy setup already in place. Komodo: ruled out on inspection — it's a Core+Periphery agent architecture built for managing *multiple* servers from a dashboard, the wrong shape for one droplet, and confirms the original (thin) rejection reasoning was actually right. Docker Swarm (single-node `docker stack deploy`): already built into the running Docker Engine, real declarative reconciliation, no new tool — a genuine option that hadn't been on the table before. Terraform/OpenTofu: different layer (provisions the droplet/DNS itself), not a real contender.

**Landed on a plain script, correcting an earlier undersell of it.** `docker compose up -d --remove-orphans` already does real reconciliation (removes services dropped from the compose file) — the "no idempotent convergence" objection to a hand-rolled script wasn't as true as it sounded a session ago. Given this droplet has no real user traffic yet to protect with Kamal's zero-downtime rolling deploys, and no secrets sprawl yet to justify Ansible's vault templating, the fancier tools are solving problems this project doesn't have. Explicitly framed as revisitable once either of those becomes real, not a permanent call.

**Rollback: explicitly out of scope, reasoning talked through rather than assumed away.** Walked through what a script-based rollback would actually need: CI already tags images by git SHA in GHCR (found while checking, `api.yml` was already pushing `:latest` + `:${{ github.sha }}` — compose just never used the SHA tag), so the version-pinning half exists; a rollback script would need compose to reference a variable tag instead of the literal `latest`, plus a small release-log so `rollback.sh` knows what to revert to. Named the real unsolved piece: rolling back the app image doesn't roll back a Drizzle migration that already ran, and that gap exists regardless of which deploy tool is used — it falls back to the pg_dump restore built on day five's first session, not something any of Ansible/Kamal/a script solves for free. Decided not to build any of this now; not enough at stake yet.

**CI's SSH credential: forced-command key, not the existing full-access one — reopening and resolving a question parked twice before.** SSH-from-CI was rejected on `push-service`'s README and again on day four, both times because it meant "a production-capable key sitting in GitHub Actions secrets." What changed: the credential itself no longer has to be production-capable. A forced command in `authorized_keys` (`command="/root/bystrek/deploy.sh"`, `no-pty`, `no-port-forwarding`, `no-agent-forwarding`) means whatever CI sends, the droplet only ever runs one fixed script — that's the mitigation both earlier rejections were missing, not a new argument for trusting CI more.

**Combined the two per-service deploy jobs into one after hitting a real race condition.** Original design had `api.yml` and `ui.yml` each carry their own `deploy` job against the same `production` environment — reasonable-looking, but editing both workflow files in the same push (exactly what building this feature required) triggered both simultaneously, requiring two separate approvals for what's really one droplet-wide redeploy. Worse: the two `deploy.sh` invocations raced on the same containers — the `ui` run failed with `removal of container ... is already in progress` while `api`'s ran concurrently. Fixed by merging `api.yml`/`ui.yml` into one `deploy.yml`: `test-api`/`build-api` and `test-ui`/`build-ui` run unconditionally in parallel (deliberately not path-filtered per job — conditional diff logic across all trigger types, including `workflow_dispatch` and force-pushes, is exactly the kind of edge-case-prone complexity this project avoids; rebuilding an unchanged image is cheap and harmless), both feeding one `deploy` job. One approval, one SSH call, structurally no race.

### What we actually built

- **Dedicated ed25519 keypair** (`~/.ssh/id_ed25519_bystrek_deploy`), added to the droplet's `authorized_keys` *alongside* the existing full-access key, not replacing it, with the forced-command restriction above.
- **`infra/deploy.sh`** (`cd /root/bystrek && docker compose pull && docker compose up -d --remove-orphans`), scp'd to `/root/bystrek/deploy.sh`, `chmod +x`.
- **Manually verified the restriction before trusting it in CI**: `ssh -i <newkey> root@host whoami` ran the deploy script and never returned `root`; a port-forward attempt (`-L`) got `channel N: open failed: administratively prohibited` in verbose SSH output, confirming the server-side refusal (a naive `nc -z` check on the locally-bound port looked like it succeeded and was misleading — the client-side listener binds fine regardless of what the server later refuses, so that alone doesn't prove anything).
- **GitHub Environment `production`** via `gh api`: required-reviewer protection rule (worked fine on this private repo — no plan-tier paywall hit), `main`-branch-only deployment policy, two environment-scoped secrets (`DEPLOY_SSH_KEY`, `DEPLOY_HOST`).
- **`.github/workflows/deploy.yml`**, replacing `api.yml`/`ui.yml`: four test/build jobs (unconditional), one `deploy` job (`needs: [build-api, build-ui]`, `environment: production`), plain OpenSSH in the run step rather than a third-party Marketplace action — consistent with keeping new trusted surface area low.
- **Watchtower removed**, repo and droplet both, only after the new path was proven working via a real approved run.
- Docs updated to match: `whats-next.md` item 3 rewritten from a plan into a "done," item 1's summary and item 2's `api.yml`/`ui.yml` references fixed to match the merged workflow, `infra/README.md` updated to explain `deploy.sh`'s new (partial) role.

### Problems hit along the way (and the actual fixes)

- **First real CI run failed**: `Load key ... error in libcrypto`, then `Permission denied (publickey)`. The private key file written by `printf '%s' "${{ secrets.DEPLOY_SSH_KEY }}"` was missing its trailing newline after `-----END OPENSSH PRIVATE KEY-----` — the secret's stored value apparently didn't round-trip its trailing newline, and `%s` alone doesn't add one back. Fixed with `printf '%s\n'`. Caught by the first real CI run, not by local testing (the local key file was always well-formed — this only ever manifested through the GitHub secret round-trip), which is exactly the value of insisting on a real end-to-end run over trusting the YAML on review.
- **The `ui` deploy job's second failure was the concurrency race** described above (`removal of container ... already in progress`), fixed at the workflow-structure level (see decisions above), not by adding retry logic to the script.
- **Race left a container with a stale internal name** (`a7393ea5cb03_bystrek-api-1`, a Compose rename-before-remove artifact) — everything was still `Up`/healthy and serving correctly, and a single uncontended re-run of `deploy.sh` cleared it without any manual container surgery. Confirmed it wasn't a symptom of anything deeper by checking `docker compose ps` labels, not just the display name.

### Current state

CI-triggered deploy is live, proven through a real approved run end to end (`test-api`/`test-ui`/`build-api`/`build-ui`/`deploy` all green, container recreated on the droplet, both sites smoke-tested afterward), and Watchtower is gone from both the repo and the droplet. `whats-next.md` item 3 closed out. Next real work is item 4 (calendar), unchanged from before this detour.

**Addendum, same session: tried required status checks on `main`, reverted.** Wanted PR merges gated on `test-api`/`test-ui`/`build-api`/`build-ui` passing. Learned the hard way (a real rejected `git push`) that GitHub's required-status-checks — ruleset or classic branch protection, same underlying mechanic — block *any* commit landing on the branch, direct push or PR merge alike, since a brand-new commit can't already have a passed check. There's no native "PR-only" mode. The one workaround (an `OrganizationAdmin` bypass actor, `bypass_mode: always`) would have exempted the sole account from the rule entirely, direct pushes and PR merges both — pointless for a single-maintainer repo, so not worth the added ceremony. Reverted to: `deploy.yml` still runs tests/builds on PRs (`pull_request` trigger added, `deploy` job stays guarded to `push` events only, images only get pushed to GHCR on real pushes to `main`) — checks are visible on any PR, nothing enforces them. Deliberately keeping discipline manual rather than fighting GitHub's model for a solo project. If a real collaborator ever joins, this is worth reopening.
