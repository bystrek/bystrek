# Day Ten — bystrek.dev

**Date:** 2026-08-20
**Goal:** Execute the decided SvelteKit → Angular migration (`docs/frontend-migration.md`) — full re-port of login, push notify, and household admin, restructured into separately routed pages instead of one big conditionally-rendered page, on a modern Angular setup (zoneless, standalone, esbuild/Vite builder).

## What we decided

**Full re-port today, not just login + main screen.** Chose the bigger scope over a smaller "prove the skeleton" slice, since the current app is genuinely tiny (3 route files, one `auth.ts` helper, one service worker) — small enough that finishing everything in one session was realistic, and it avoids leaving `ui/` in a half-SvelteKit, half-Angular state across sessions.

**CSR-only, no SSR.** The app is entirely auth-gated behind a client-only bearer token in `localStorage` — no SEO/conversion pressure, same reasoning `frontend-migration.md` already used for why the Svelte-vs-Angular bundle-size gap doesn't matter here either. `ng new --ssr=false`.

**`fileReplacements` (`environment.ts`/`environment.prod.ts`) instead of the `PUBLIC_API_URL` Docker build-arg.** The API origin was never secret — it was already sitting in plaintext in `deploy.yml`. Baking it via Angular's standard `production` configuration removes a moving part (no more `ARG`/`ENV` threading through the Dockerfile, no more `build-args:` line in CI) for zero real cost, since the value essentially never changes and isn't sensitive.

**A dependency-free `Bun.serve` script (`ui/server.ts`) instead of nginx or `serve`/`http-server`.** Matches the same "small custom script over a heavier tool" pattern as `infra/deploy.sh`. SPA fallback (unknown paths → `index.html`) is load-bearing, not cosmetic — `/login` and `/auth/reset-password` are real URLs hit as fresh navigations (a password-reset email link isn't a client-side route transition), so the server has to resolve them to the app shell, not 404.

**One `authInterceptor` applied uniformly, including to the unguarded `/push/*` routes**, rather than a separate unauthenticated `HttpClient` for push calls (mirroring the original's split between `authFetch` and plain `fetch`). The push endpoints don't read the `Authorization` header at all, so an extra bearer token showing up there is inert — simpler to have one interceptor and no special-casing than to carry the old split forward for no behavioral reason.

**`signIn()` and `initSession()` stay decoupled**, matching the original `+page.svelte`'s explicit two-step orchestration (`await signIn(...); session = await getSession();`) rather than having `signIn()` call `initSession()` internally. First pass did couple them; walked it back for two reasons — it matches what the original code actually did (not an arbitrary simplification), and it made `AuthService`'s own unit tests much simpler: each test now issues exactly one HTTP call instead of needing to hand-drain microtask chains between a mocked response and the next dependent request `HttpTestingController` would otherwise need to see.

**Signals for everything that mutates after an `await`.** Zoneless Angular only reliably re-renders on a signal write (or `markForCheck`/async pipe) — a plain class field mutated inside code that resumes after an `await` boundary isn't guaranteed to trigger change detection, since Angular's own event-dispatch notification only covers the synchronous portion of a handler. Every piece of state that changes after a network call (`PushService.status`/`subscribed`/`busy`, `HouseholdService.household`, `AuthService.session`, form fields bound via `[ngModel]="x()" (ngModelChange)="x.set($event)"`) is a signal for this reason — not a stylistic preference.

## What we actually built

**Structure**: `core/auth/` (`AuthService`, `authInterceptor`, `authGuard`/`guestGuard`), `core/push/` (`PushService`), `core/household/` (`HouseholdService`), `features/{login,main,reset-password}/` (one component each). Routes: `/login` (`guestGuard`), `/auth/reset-password` (unguarded either direction), `''` → `Main` (`authGuard`), `**` → redirect to `''`. `provideAppInitializer(() => inject(AuthService).initSession())` resolves the session once before the router activates, so the guards never race an unresolved signal on first paint.

`Main` hosts push controls (exact button text/ids preserved: "Enable notifications"/"Subscribed"/"Send test notification", `#status`) plus a new signed-in indicator + sign-out, plus the household section (`#household`, `#invite` admin-only, "Ban"/"Unban") — same layout as the old single page, now gated by routing instead of inline conditionals. Global styles (`src/styles.css`) carry the shared body/button/input look; each feature keeps only its own structural CSS, mirroring how the original Svelte `<style>` blocks were already per-component scoped.

`sw.js`, `apple-touch-icon.png`, `robots.txt` moved into `ui/public/` (Angular's `application` builder copies this verbatim to `dist/ui/browser/` root, same same-origin guarantee as SvelteKit's `static/`). PWA meta tags (`apple-mobile-web-app-*`, `apple-touch-icon` link) hand-authored once into `src/index.html` — there's still no `manifest.json`, this app's "PWA-ness" has always been iOS's own meta-tag convention, not the Web App Manifest spec.

**Docker/CI**: `Dockerfile` rewritten to a build stage (`bun run build`) + a runtime stage that's just `oven/bun:1` + `server.ts` + the static `browser/` output — no second `bun install`, since `server.ts` has zero non-builtin dependencies. `deploy.yml`: dropped the `PUBLIC_API_URL` build-arg and env line, added a `bun run test` (Vitest) step to `test-ui` ahead of Playwright. `playwright.config.ts`'s `webServer.command` changed from `vite dev -- --port 4173` to `bun run start -- --port 4173` (Angular's dev server is Vite-based under the current builder, same flag). `api/.env.example`/`api/.env`/`scripts/dev.sh`: SvelteKit's `5173` dev-port default → Angular's `4200`.

**Tests**: all three Playwright specs ported — `subscribe.spec.ts` needed a new signed-in precondition (seed `localStorage['bystrek_token']` + mock `get-session`) since push controls no longer render on a guard-free page; `household.spec.ts`'s signed-out case now asserts the `authGuard` redirect (`/` → `/login`) instead of asserting `#login` directly on `/`; `reset-password.spec.ts`'s post-redirect assertion changed from `toHaveURL('/')` to `toHaveURL('/login')` — a password reset never establishes a session, so landing on `/` while signed out correctly guard-redirects now, which is more correct than the old single-page app's implicit "just show the login form on the same page" behavior. Added `auth.service.spec.ts` (Vitest, `HttpTestingController`) — the first real unit test coverage `ui` has ever had; `docs/architecture.md` already decided Vitest for this, it just never got wired up under SvelteKit.

## Problems hit along the way (and the actual fixes)

**Angular CLI 22 refuses to run on this machine's Node (v24.3.0) — it hard-requires ≥24.15.0, ≥22.22.3, or ≥26.0.0.** No `nvm`/`fnm`/`volta` installed, so bumping Node would've meant a system-wide change outside this project's scope just to unblock scaffolding. Checked `npm view @angular/cli@21 engines`: `>=24.0.0`, which the installed Node satisfies. Used Angular CLI 21.2.21 instead — one minor behind, same zoneless/standalone/esbuild-builder/Vitest defaults, confirmed by actually scaffolding with it and inspecting the output rather than assuming. Not a compromise on anything the migration actually asked for, just a version-pin forced by the local environment.

**`applicationServerKey: urlBase64ToUint8Array(publicKey)` failed to typecheck** — `Uint8Array<ArrayBufferLike>` isn't assignable to `BufferSource` under the current TS DOM lib types (`ArrayBufferLike` includes `SharedArrayBuffer`, which `BufferSource`'s `ArrayBufferView<ArrayBuffer>` constraint rejects). A type-level strictness change, not a real runtime concern — a plain `Uint8Array` from `Uint8Array.from(...)` is never backed by a `SharedArrayBuffer` in practice. Fixed with a narrow `as BufferSource` cast at the call site rather than loosening anything more broadly.

**`curl -I` against the running container showed empty `Content-Type` for `/sw.js` and `/apple-touch-icon.png`**, which looked like `Bun.serve`/`Bun.file` weren't setting content types at all — worth being suspicious of rather than assuming the server was broken. Re-checked with a real `GET` (`curl -sD -`) instead of `HEAD`: correct `content-type: text/javascript;charset=utf-8` and `image/png` both present. `Bun.serve` just doesn't special-case `HEAD` requests the way `curl -I` expects; the server itself was fine the whole time.
