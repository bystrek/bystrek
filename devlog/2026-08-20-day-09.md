# Day Nine — bystrek.dev

**Date:** 2026-08-20
**Goal:** Work out how chat/LLM interaction with the calendar (and, it turned out, with every future domain) actually has to be built — before writing any of it.

## What we decided

**Calendar writes go write-through, not local-first-batched.** `create_event` pushes to `caldav.icloud.com` synchronously, then refreshes the local Postgres cache immediately rather than waiting for the next scheduled pull. The alternative — write to Postgres, mark it `pending_sync`, let a scheduled job push it up later — is the more "standard" sync-engine shape, but it means the event doesn't really exist (no notification, doesn't show on the phone) until some later job runs, and it makes us own conflict resolution between two sources of truth. Write-through keeps iCloud as the single source of truth for writes and Postgres a pure read cache; a failed CalDAV push is just a tool error reported back in the same chat turn, not a silently stuck row.

**Calendar writes auto-execute and report, not propose-then-confirm.** Reserving the confirm-before-write pattern (already decided in `architecture.md` for sensitive domains) for writes where being wrong actually costs something — calendar entries are cheap to undo via the soft-deletes already planned. This is a per-domain policy call, not a blanket one; medical/etc. will likely want confirmation.

**Frontend stays chat-only for v1 — no per-tool widget rendering yet.** The alternative (a widget component per tool, rendered inline in chat) was seriously discussed, but three things argued against building it now: it breaks the vertical-slice property where adding a domain only touches the backend (a widget-per-tool means frontend work scales with domain count too); it's a bigger surface for the pending Angular migration to re-port; and it requires the backend to start forwarding structured `tool_use`/`tool_result` events down the SSE stream instead of just final text — a real subsystem change not worth making before it's a felt need. Recorded for later, not dropped: when it does get built, the backend should own its own event vocabulary (`{type, tool, data}`) rather than thin-proxying Claude's raw stream events verbatim — keeps the frontend decoupled from the Anthropic SDK's event shape, and keeps the backend (which already owns decryption and household visibility) as the single place that decides what's allowed to reach the browser.

**Build order:** backend chat endpoints first (curl-testable in isolation, same pattern proven out during auth wiring on day eight) → Angular scaffold → re-port the existing SvelteKit login/household UI (not drop it — the whole point of building auth in SvelteKit back on day eight was that porting it once is a fixed, bounded cost) → routed login page + routed chat page → chat component → wire to backend.

**Persist chat history from day one, as a single continuous thread per user — not discrete "new chat" conversations.** The single-thread shape was chosen specifically because item 8 (proactive nudging) needs the assistant to be able to inject into an *existing* conversation later ("did you actually go to that appointment?"); a discrete-conversations model would force nudges to awkwardly spawn new threads. Store the **full raw Claude message sequence**, including `tool_use`/`tool_result` blocks, not a simplified `{role, text}` transcript — storage cost is trivial next to the value of Claude having exact memory of what it actually did on a prior turn, not just its own prose summary of it. The `messages` table is the first to carry `owner_id`/`visibility` (`private`, no household-shared conversations, unlike calendar) and tier-2 field encryption — patterns already decided in `architecture.md` for domain tables generally, now actually landing somewhere.

**Context sent to Claude per request is a bounded recency window, not the full stored thread.** This was the one real correction mid-session: single-continuous-thread-forever obviously means unbounded context growth, and the first instinct was rolling summarization (compact older messages via a periodic LLM call). Talked out of it: summarization is a whole new standing subsystem (a compaction job, maintained forever) for a problem two cheaper options already cover. Landed on recency window now (trivial — `ORDER BY created_at DESC LIMIT N`) plus retrieval-as-a-tool later if the window ever proves insufficient — a `search_chat_history` tool backed by `pgvector`, which is already in the decided stack (`Postgres (+pgvector)` on the architecture diagram) and isn't a new mechanism, just another entry in the same tool registry calendar/etc. already need.

## Problems hit along the way

None in the build sense — nothing was built. One terminology correction worth recording: early on, "MCP" got used loosely for what's actually just the Anthropic Messages API's native tool-use feature (a `tools` array in a plain HTTPS request). MCP (Model Context Protocol) is a different, unrelated mechanism for connecting external tool servers to a client — bystrek's backend never needs it, since the backend itself is both the thing calling Claude and the thing running the tool implementations.
