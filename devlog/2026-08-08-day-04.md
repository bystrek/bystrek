# Day Four — bystrek.dev

**Date:** 2026-08-08
**Goal:** Lock the tech stack for the day-four platform build — frontend, backend framework, ORM, runtime, auth — and sequence the build order, before writing any code.

## What we decided

### Frontend: SvelteKit, no Vercel AI SDK, RxJS

Considered Angular first (matches prior experience) but it has no maintained streaming/tool-call chat library. Once that mattered less (see AI SDK below), Angular came back into play but lost to Svelte on merits: compiler-based reactivity, mutation-friendly state (no immutable-rebuild ceremony like Solid/Qwik) fits streaming chat state well, and the best PWA story of the options considered — matters since this app absorbs `push-service`'s `sw.js`. Solid and Qwik considered and dropped (Qwik's resumability doesn't pay off for an installed PWA; Solid's RxJS interop is an adapter, not native).

Dropped Vercel AI SDK: its two selling points (multi-provider abstraction, maintained per-framework hooks) don't apply to a Claude-only app. Talk to `@anthropic-ai/sdk` directly, hand-write the multi-step tool-call loop (~30–80 lines).

RxJS on the frontend to consume the SSE stream: not required (a plain async generator would work), but its operators solve real chat-UI races (e.g. `switchMap` cancelling an in-flight stream when a second message is sent) and an RxJS `Observable` satisfies Svelte's store contract natively.

### Backend framework: NestJS

Deciding requirement: proper DI (a real IoC container), not context-decoration tricks. Ruled out on that basis:
- **Elysia** (Bun-native, considered for its runtime speed) — `.decorate()`/`.derive()`/`.resolve()` are DI-*like* but not a real container (no token-based resolution, no constructor injection). Pairing it with a standalone container like Awilix would have fixed this but wasn't pursued once Nest proved sufficient on its own.
- **Alosaur** (Deno) — has real DI, initially looked promising once we verified it wasn't abandoned (811 stars, 21 contributors, recent commits), but Deno itself got rejected separately (smaller ecosystem than the Bun options, DB-driver support unverified) and Alosaur's Guard/Interceptor-equivalent hooks were never confirmed either.
- **Deepkit** — the most technically impressive DI of anything evaluated (genuine interface-based injection, more capable than Nest's own). Rejected purely on risk, not merit: self-declared alpha with APIs still moving, a 2025 EU trademark loss to an unrelated, unconnected company (Deepki, a Paris ESG-data firm — real signal of institutional fragility, not just a naming footnote), adoption 20–1000x smaller than Nest on every metric checked (stars, downloads, production examples), no 2026 release, and a live, unresolved Bun compatibility bug with zero other projects depending on the plugin. Too much risk for a platform meant to hold medical records for years, however good the tech.

### ORM: Drizzle

Also compared TypeORM and MikroORM, both real contender given prior Doctrine (Symfony) experience — TypeORM's decorator/entity/repository style is the closest analog to Doctrine of anything in the TS ecosystem, and MikroORM is even more faithfully Doctrine-shaped (explicitly Data Mapper + Unit of Work + Identity Map, same three patterns). Both rejected for the same root reason: that Unit-of-Work/Identity-Map architecture is exactly what produces Hibernate's classic silent-N+1-query problem — confirmed as a real, current, named issue specifically in TypeORM. MikroORM has engineered real mitigations (type-checked populate hints, stricter-by-default since v5) but still carries residual Unit-of-Work complexity (manual `RequestContext` scoping per request in Nest).

Prisma was the strongest remaining option — no lazy-proxy risk (explicit `include` only), best nested-write ergonomics, a real field-encryption mechanism (`Client Extensions`) that maps directly onto the tier-2 encryption requirement, official NestJS docs recipe. Lost specifically because it abstracts SQL away behind a schema DSL and generated client — the opposite of the hands-on SQL practice this project is also meant to build. Drizzle mirrors real SQL almost 1:1, has zero lazy-proxy risk (explicit `with`, same as Prisma), and has genuinely native (not retrofitted) Bun support. Real costs accepted: no built-in encryption hook (must wrap encrypt/decrypt manually at every call site — a discipline requirement), and NestJS integration is unofficial (hand-write a thin provider; there's an open, unresolved GitHub issue asking Nest's docs team for an official recipe).

### Runtime: Bun

The original hesitation was two unofficial integrations stacked on each other (Nest-on-Bun and Prisma-on-Bun). Choosing Drizzle removed the second one entirely — it has dedicated, official Bun modules. What's left is only Nest's own Bun compatibility: works, ~90%+ Node/npm compat, not officially blessed, a community starter (`bunest`) that flags itself as not production-ready. Accepted specifically because this decision is cheap to reverse — Nest CLI compiles to plain JS regardless of runtime and Drizzle runs identically on both, so falling back to Node later is a Docker base-image swap, not a redesign. Unlike the framework/ORM choices, the reversibility justified a lower bar for accepting residual risk.

### Auth: switch from Sign in with Apple to passkeys + magic link

`docs/architecture.md`'s auth section (written day three) had picked **Sign in with Apple** as the sole login method to start. Revisited it right after the stack lock and switched to **passkeys (WebAuthn), invite-gated, with magic-link email as fallback**.

Two reasons: it avoids the paid Apple Developer Program enrollment ($99/yr) that Sign in with Apple requires (Services ID, Sign in with Apple key, Team ID) purely for login, and it keeps auth off third-party identity providers entirely — consistent with the project's self-hosted, own-your-data pattern already applied to `better-auth` itself (see the earlier Auth0/Okta rejection). No public signup: an admin creates a pending household-member record plus a signed invite token, and the invite link runs `better-auth`'s passkey-first flow. Magic link, sent to the email captured at invite time, covers device loss.

### Build locally first, deploy after

The original `whats-next.md` plan interleaved infra (provision droplet Postgres, DNS, Caddy site block for `api.bystrek.dev`) with the actual scaffolding steps. Pushed back on that: no reason to touch production DNS/Caddy before there's any code to deploy.

Checked whether that was actually safe given passkeys and push both sound origin-sensitive: WebAuthn's spec explicitly treats `localhost` as a valid secure context for its RP ID, and service workers get the same secure-context exemption — so both the passkey/invite flow and push can be built and tested entirely on a laptop, no `api.bystrek.dev` required. That removed the only two things that looked like they might force early deployment. CalDAV sync is just an outbound HTTPS call either way, indifferent to where it runs from.

Revised order: local Postgres (Docker, dev-only, kept separate from the droplet's compose file) → scaffold backend + frontend locally → build the calendar vertical slice end-to-end locally → only then provision droplet Postgres, DNS, and the `api.bystrek.dev` Caddy block, and cut `push-service` over to internal-only.

### Email delivery for magic-link fallback: Resend

Audited the docs for an existing decision on this (architecture.md, whats-next.md, prior devlog entries) — never addressed. The passkey path itself needs no email sender, but the magic-link fallback can't be built, even locally, without picking one.

Considered Resend, Postmark, and reusing existing SMTP (Fastmail). Went with **Resend**: simple API, generous free tier, nothing to self-host or configure at the SMTP-server level. Postmark has stronger deliverability pedigree but no meaningful free tier for a single-household app this size. Reusing personal SMTP was rejected — it would work, but hands the app both deliverability and rate-limit ownership for no real benefit over a purpose-built transactional API.

### Day-four scope: defer auth, encryption, chat UI, and calendar

Revisited scope after the stack/auth/local-first decisions above: auth (passkeys/magic-link) and tier-2 encryption have nothing to gate or protect yet — no schema exists. Chat UI and the calendar vertical slice are real features, not scaffold-proving work. Cut all four from today; today stops at a proven, deployed scaffold (backend + frontend talking to each other, for real, on the droplet).

### Fold push-service into the new backend/frontend

`docs/architecture.md` had `push-service` staying as its own internal-only service, called by the backend API. Reconsidered once `bystrek.dev`'s root route came up as a real collision (the new frontend and `push-service`'s subscribe page can't both own it): `push-service` is ~74 lines (Hono + `web-push` + a SQLite subscriptions table), and its own `app.ts` already flagged its root route as "temporary... until the custom app takes over." Keeping a whole separate container, Docker network hop, and CI workflow for that little logic isn't worth it now that the app that was always going to absorb it actually exists.

Concretely: the `subscriptions` table moves from `push-service`'s SQLite into Postgres via Drizzle; `/push/vapid-public-key`, `/push/subscribe`, `/push/send` port into Nest verbatim (same `web-push` library, same VAPID env vars); `index.html`/`sw.js`/the touch icon move into SvelteKit, served at its root. Sequencing caution: don't cut the droplet's Caddy route away from `push-service` until the new stack is verified sending a real push — it's the one thing currently working in production, and there should never be a window where it's fully down.

Added a manual "Send test notification" button to the new frontend (there wasn't one before — `push-service`'s `/push/send` was only ever called via `curl`). Turns out to double as the actual verification step for the whole migration, both locally and after the droplet deploy: it proves the full frontend → backend → phone path, not just the backend in isolation. No new exposure — `bystrek.dev` is already Tailscale-gated, same trust boundary `/push/send` already relied on.

### Migrations: run automatically at container boot

Considered running Drizzle migrations as a manual step (matching `push-service`'s existing manual `docker compose pull && up -d` deploy). Went instead with auto-migrate in the entrypoint (`drizzle-kit migrate` before the app starts): this is a single-instance droplet, not a rolling/multi-replica deploy, so there's no concurrent-migration race to guard against. The usual objection to boot-time migrations (unreviewed schema changes hitting prod) doesn't apply either — Drizzle migrations are generated SQL files committed ahead of time, so review already happened at PR time. A failed migration fails the container loudly instead of the app running against a stale schema, which is the right failure mode here.

### Deployment: Dockge + Watchtower, not GitOps or SSH-from-CI

Wanted "proper CD" without reopening the tradeoff `push-service`'s README already reasoned through and rejected: SSHing from CI into the droplet means a production-capable key sitting in GitHub Actions secrets. That calculus is worse now, not better — this backend will eventually sit in front of Postgres holding medical records, not just push subscriptions.

Walked through the real options:
- **SSH-from-CI** — rejected again, same reason as `push-service`, higher stakes now.
- **Self-hosted GitHub Actions runner on the droplet** — avoids shipping a key off the box, but a runner is a well-known escalation path: anything that gets a workflow to run (bad dependency, malicious PR) executes with the droplet's own permissions.
- **ArgoCD** — built for Kubernetes, reconciles against a cluster API server. No cluster exists here and adopting one (k3s) just to get GitOps would mean re-platforming Caddy, Postgres, and secrets — a full infra migration motivated by tooling preference, not an actual problem hit.
- **Portainer Git-Stacks** — the actual Docker-Compose-world analog to ArgoCD (reconciles the whole compose file from git, not just image digests). Polling mode avoids a new inbound surface, webhook mode reopens one. But the config-reconciliation benefit only matters if the droplet's live `docker-compose.yml` becomes git-tracked and auto-pulled — a reversal of the established "infra managed by hand, synced via `scp`" pattern, and a separate decision from picking a CD tool. Also itself a bigger, more privileged permanent component (full management API/UI) than the alternatives below.
- **Watchtower alone (polling, image-digest-only)** — no new inbound surface, but needs `/var/run/docker.sock` mounted, which is close to root on the host. A real cost, worth naming honestly rather than treating a polished tool as free.
- **Plain script + systemd timer** — literally the existing manual `docker compose pull && up -d` on a timer. No new component, no new privilege beyond what's already trusted.

What was actually wanted, once described precisely, turned out to be simpler than any of the above: a dashboard to see what's running and its logs, with a manual pull-and-redeploy button. That's not automatic CD at all — it's a nicer interface for the same manual step, triggered by a human on the tailnet, same trust model as SSHing in today. **Dockge** fits that directly (compose-native, lighter than **Portainer CE**, which does the same job but carries Swarm/Kubernetes-oriented surface this project doesn't need).

Then asked for automatic deploy on top of that anyway, specifically because it derisks future work. **Watchtower** pairs cleanly with Dockge: Dockge's stacks are ordinary `docker compose`-managed containers underneath, which is exactly what Watchtower expects to operate on (it recreates a container in place, preserving config/labels/volumes — a very common pairing with Compose). Label-scoped (`--label-enable` + a label on just the new backend/frontend services) so it leaves Postgres/Caddy/Dockge itself alone. Net result: Watchtower handles the routine "new image landed" case automatically; Dockge remains for visibility, manual overrides, and anything Watchtower can't catch (compose/config changes, since it only watches image digests). Accepted cost: another container with Docker socket access, on top of Dockge's — not a new class of risk, but a wider blast radius if either is compromised.
