# Day Fifteen — bystrek.dev

**Date:** 2026-09-02
**Goal:** Debug why chat has been getting weekdays and week windows wrong (issue #18), then figure out how to actually see what the tool loop is doing when it acts up. First half is the model fix; second half is a scope-and-design conversation that ended in a follow-up issue for a small self-hosted observability stack, not code.

## What we decided

**Move weekday-for-date and today→week-window arithmetic out of the model, into deterministic backend code that hands the model the answers directly.** The [[project_llm_date_bug|fresh repro on 2026-09-01]] made the failure mode clear: the model had today's weekday in the system prompt (via `Intl.DateTimeFormat({weekday: 'long', ...})`) and each event's ISO timestamp in the tool result (via `zoned-time.ts:formatZonedIso`), and still called `2026-09-06T16:00:00+02:00` a Saturday and named "this week" as `1–7 września`. So more context wasn't going to help — the input was already there. The arithmetic step was the failure. The right fix is not asking the model to do that arithmetic at all.

Two deterministic inserts:

- **System prompt.** New sentence with Mon-Sun bounds for both this week and next week, English weekday label on each end date, computed in the user's timezone via `Temporal.ZonedDateTime.dayOfWeek`. Handles the Sunday-boundary edge case natively — on a Sunday, "this week" ends today and "next week" starts tomorrow, which the model was also getting wrong in the repro.
- **Calendar tool output.** Every `ParsedEvent` gains `startWeekday`/`endWeekday`. Prompt now says "relay times **and weekdays** as given, never re-derive them" — extending the existing "never reinterpret" rule for datetimes.

**English weekday names across all locales, not localized per user.** The LLM translates day names reliably (that's the easy part of its job); the arithmetic was what was going wrong. One code path, no `Intl` abbreviation quirks across locales, and no per-locale name table to keep in sync.

**Format split between the two inserts, natural language vs structured:**
- System prompt uses a plain English sentence, matching the shape of the existing "The current date and time is X" line. LLMs parse a short factual sentence more reliably than a JSON blob, and it's more token-efficient for two facts.
- Calendar tool output already returns JSON to the LLM, so weekday goes in as a sibling `startWeekday`/`endWeekday` field alongside `start`/`end` — keeps `start` machine-parseable if a follow-up tool ever consumes it, and gives the LLM the label right next to the value.

## What we actually built

**PR #28** (merged). `api/src/calendar/zoned-time.ts` gained `weekdayName(date, timeZone)` and `weekBoundsAround(date, timeZone)` — both English, both computed via `Temporal`. `api/src/calendar/ical-event.ts:ParsedEvent` gained `startWeekday`/`endWeekday`, populated by `parseEventIcs`. `api/src/chat/chat.service.ts:buildSystemPrompt` calls `weekBoundsAround(now, timezone)` and appends the Mon-Sun sentence, and now instructs the model to relay weekdays alongside times.

Tests: new blocks in `zoned-time.spec.ts` for both helpers, including the Sunday-boundary edge case and the exact 2026-09-06/07 dates from #18. `ical-event.spec.ts` gains a case asserting `startWeekday === 'Sunday'` for `2026-09-06T16:00:00+02:00`.

## Continuation: tool-call debug logging, scope and design

### What we decided

**Log tool calls, but do it properly in a follow-up issue — not in the same PR as the model fix.**

The first pass at PR #28 also added a Nest `Logger` to the `ChatService` tool loop, printing `tool.request`/`tool.response` lines with the full LLM input and tool output to Docker stdout. Copilot flagged it: calendar tool outputs include event summaries/descriptions/locations, which becomes user PII in `docker logs api` and anything downstream (aggregators, backups, temporary access grants). Legit concern, especially since the notes/medical/nutrition/gym domains on the [[project_roadmap|post-MVP roadmap]] all raise the same class of leak by more.

Walked through the option space in full rather than picking the first "encrypt it" answer. Rejected:
- **App-side encryption of the log body**, keeping stdout-to-Docker logs (option "C1" in the conversation). Works, but on a single-droplet setup `.env` (holding `ENCRYPTION_KEY`) lives on the same box as the log file — anyone who can read the log can also read the key. Defends against a very narrow "log leaked, `.env` didn't" scenario that doesn't correspond to a realistic access path.
- **SaaS log service** (Grafana Cloud, BetterStack, Papertrail, Axiom, etc). Ships user calendar/notes/medical content to a third party. Regression against the [[project_domain_identity|non-identifying bystrek.dev]] posture, and worse when tier-2 domains land.
- **SigNoz / HyperDX** (ClickHouse-backed OTel stack). Beautiful "logs + traces + metrics in one UI" story and the best CV bullet of the shortlist (OpenTelemetry is the hot keyword right now), but SigNoz's own docs recommend 4 GB RAM minimum. On a 2 GB droplet with Postgres + `api` + Caddy + Dockge already resident, it's OOM territory, not "tight but doable".
- **Loki + Grafana** (with OTel Collector as the shipper). ~450 MB idle. Fits the droplet if we set per-container `deploy.resources.limits.memory`, and gives the same OTel-keyword CV story via the Collector step. But 450 MB against ~1 GB headroom is close enough that a chat-under-load spike could still push the box over; user preferred to keep more margin.
- **Custom Nest logs microservice.** Rejected as make-work — building a log platform in a personal app pays off only when the OSS options don't fit for a specific reason, and here they do.

Chosen (tracked in issue #29, not built this session): **Vector as the log shipper + Dozzle for a browser view, both bound loopback-only, accessed via SSH tunnel — same pattern as Dockge.** ~45 MB resident total, no third-party data flow, plaintext bodies with filesystem access as the auth boundary. Plus DuckDB installed on the droplet as the ad hoc SQL escape hatch (`duckdb -c "select ... from read_json_auto('/var/log/bystrek/tools.log') where ..."`) when grep isn't enough — zero resident cost until invoked.

Encryption of the log file itself was reconsidered under Vector-with-private-file storage and rejected again for the same reason: `.env` sits on the same box, so a threat model that reads the log file also reads the key.

CV framing came up explicitly (this project doubles as portfolio material) and steered a few of the rejections. SigNoz would have been the strongest single line item, but "started with a minimal shipper, wired in Loki + OTel Collector when observability needs grew, considered SigNoz but rejected it on resource grounds for a 2 GB droplet" is honestly a better story on a CV — shows judgment, not just tool-picking. Same shape holds if this ever grows into A1 later: the swap of storage backend is the substantive change, not a rebuild.

## Problems hit along the way (and the actual fixes)

- **Local Bun 1.3.14 doesn't have Temporal.** `package.json` pins `bun@1.4.0` via `packageManager`, but corepack doesn't manage Bun and nothing enforces the local install — so `bun test` fails on every `zoned-time.spec.ts` line, including pre-existing ones. Not caused by this session; noticed via the new tests. CI uses `oven-sh/setup-bun@v2` which respects the pinned version, so tests run for real there. Nothing to fix locally beyond bumping the dev machine's Bun; noted for future runs.
- **Copilot posted a legitimate PII-in-logs concern faster than a human reviewer would have.** Worth remembering that a Copilot pass on chat-adjacent PRs is genuinely useful — this one steered the whole logging design toward the Vector setup instead of shipping a leak. Not a fix, an observation: `/code-review copilot` is worth the ~5 min it costs on anything touching user content.
