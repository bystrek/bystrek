# Day Three — bystrek.dev

**Date:** 2026-08-07
**Goal:** Notifications — chat on Mac (or anywhere) → push on phone, per item 1 of `whats-next.md`.

## What we decided

**Rejected the original ntfy-app plan.** The initial idea (self-host ntfy, install the ntfy iOS app) worked technically but meant a dedicated app the user didn't want.

**Rejected ntfy + Web Push on its own subdomain.** Checked ntfy's docs directly: it explicitly does not support being reverse-proxied under a subpath, and its Web Push feature is tied to serving from its own origin. So `ntfy.bystrek.dev` next to `bystrek.dev` (Open WebUI) would unavoidably mean **two separate home-screen icons/PWAs** — not the unified experience wanted.

**Rejected a native iOS app talking to APNs directly.** Confirmed iOS Web Push (available since iOS 16.4, for home-screen-installed web apps) already routes through Apple's real push service under the hood — there is no more-direct "raw APNs" path available to a website. A genuinely native app would need an Apple Developer Program enrollment ($99/yr), Xcode, and either that fee or re-signing from a Mac every 7 days — strictly worse than Web Push for this goal, and still a second icon.

**Landed on: build our own small self-hosted Web Push service, same origin as Open WebUI.**
- A minimal HTTP service serving a service worker and push endpoints under `bystrek.dev` itself (e.g. `bystrek.dev/push/*`), so the browser's push subscription is scoped to the *same* origin/PWA install as the chat. One home-screen icon (`bystrek.dev`), real APNs-backed delivery via the standard browser Push API, no native app, no App Store, no second icon.
- Own VAPID keypair, own tiny subscription store — no ntfy involved for delivery. Trade-off going in: we lose ntfy's off-the-shelf polish (dashboard, retries, priorities) in exchange for unification; still get `notificationclick` action-button handling for the later proactive-nudging goal (item 4 in `whats-next.md`).

**Stack for the microservice: Bun, no monorepo tooling.**
- **Bun** over Deno — `web-push` (the standard VAPID library) runs on Bun with no shims, `bun:sqlite` is built in for the subscriptions table, Docker image stays small and cold-starts fast.
- **No Nx / Turborepo** — one deployable service doesn't justify a monorepo build system. If more JS services show up later, plain Bun/pnpm workspaces is the next step up, not Nx.
- **CI**: deferred as a stretch goal, not a blocker for tonight — scope is repo + service + Dockerfile + wiring into the existing droplet compose stack, so the evening stays focused on shipping notifications rather than DevOps tooling.

## Side quest: brand mark

Before the repo was ready, spent time on a logo — cream background, two cherries connected by a stem, used as the site logo, favicon, and GitHub org avatar. Kept it inside the existing brand system rather than inventing a new one: same cream/wine/brass palette and Bodoni Moda wordmark as the day-one landing page, so the mark reads as a continuation, not a rebrand.

**Design:** single flat wine-bordeaux silhouette on cream — two circles for the cherries, one continuous curved stem stroke connecting them (no separate leaf; drawn, then removed per feedback since it read as clutter). Kept deliberately simple so it survives a 16×16 favicon. Doubles as a wax-seal-style stamp, echoing the rotating wax-seal motif already on the landing page.

**Iteration, based on feedback:**
- First pass had both stem arms curving *away* from each other (like two parentheses) — read as broken/unnatural. Fixed by making both arms lean gently *toward* the shared centerline instead.
- Right cherry originally sat too far below where its stem reached, with the stem barely tangent to the fruit instead of overlapping it. Leveled the two cherries much closer in height and pulled both stem attachment points solidly inside their circles.
- Leaf (originally at the stem's peak) removed entirely — final mark is just the two cherries and the stem.

**Deliverables**, all in `brand/`:
- `mark.svg` — silhouette alone, transparent background
- `icon.svg` / `icon-dark.svg` — cream-tile / wine-tile versions (favicon, app icon, GitHub avatar source)
- `icon-twotone.svg` — brass stem, wine/cherry fruit — for larger formats
- `export/` — rendered PNGs: `favicon.ico` (16/32/48, hand-packed PNG-in-ICO since no Pillow was available), `favicon-{16,32,48}x{...}.png`, `apple-touch-icon.png` (180), `icon-192.png`, `icon-512.png`, `logo-1024.png`, `mark-1024.png`, `icon-twotone-{512,1024}.png`

Rendered with Node + `sharp`, installed locally into the scratchpad rather than system-wide — Homebrew on this machine is owned by a different user account, so `brew install librsvg` would have needed `sudo chown` on shared system directories; skipped that rather than touch shared ownership for a one-off render.

Iterated live in a published Artifact (specimen sheet showing the mark, palette, lockup, icon tiles, avatar crop, and true-pixel favicon sizes) so changes could be reviewed visually before being written into the real `brand/` files.

## Side quest: GitHub SSH access

Needed SSH access to the new private GitHub org repo (`bystrek/bystrek`) before the push-service work in the plan above could start.

- Generated a **new** ed25519 keypair (`~/.ssh/id_ed25519_new`) specifically for GitHub — kept deliberately separate from the droplet's existing `~/.ssh/id_ed25519`, which remains untouched and is still the sole key authorized on the droplet. (Initial ask was phrased as "delete the current key and generate a new one," which first read as a droplet-key rotation — paused before touching the droplet's `authorized_keys` and confirmed the actual intent was a GitHub-only key.)
- Added the new public key to GitHub (user did this via the GitHub UI).
- First `git clone git@github.com:bystrek/bystrek.git` failed with `Permission denied (publickey)` — the key worked fine when specified explicitly (`ssh -i`), so the cause was that SSH never tries a non-default-named key file without being told to. Fixed with a `~/.ssh/config` entry pinning `github.com` to `IdentityFile ~/.ssh/id_ed25519_new` (`IdentitiesOnly yes`).
- Verified: `ssh -T git@github.com` now authenticates correctly with no `-i` flag needed.

**Status:** GitHub SSH auth confirmed working. Repo clone itself still to be done (by the user) — service scaffolding (plan steps 2–10 above) hasn't started yet.

## Repo docs, push-service build-out, and going live (2026-08-08)

Picked the plan back up: repo docs, then the push-service scaffold (plan steps 2–10), then actually shipping it. By the end of the session, push notifications work end to end on the iPhone lock screen.

### Repo docs and infra snapshot

- Wrote `README.md` and `CLAUDE.md` for the repo (private, personal-tone, not written for a public audience) — project overview/architecture/status, and working conventions (devlog-per-session, docs upkeep, no-secrets, no-fabricated-URLs, the non-identifying-domain rationale).
- Pulled `docker-compose.yml`, `Caddyfile`, and `Dockerfile` down from the droplet into `infra/` — a manually-synced reference copy, explicitly *not* a deploy source (the droplet is still edited by hand). Confirmed neither file contains a literal secret (both use env-var interpolation, `.env` stays on the droplet only).

### push-service scaffold

Built the Bun HTTP service from day three's plan: `/push/subscribe`, `/push/send` (prunes expired 404/410 subscriptions automatically), `/push/vapid-public-key`, and a service worker. Initial cut used a hand-rolled if-chain for routing in a single `index.ts`; got feedback that this looked "haphazard" for something meant to grow. Refactored to **Hono** (small, Bun-native) with routing split into `env.ts` (config/validation), `db.ts` (`bun:sqlite`), `app.ts` (routes), `index.ts` (just starts the server) — re-ran the same smoke tests against the refactor to confirm no behavior changed.

### Deploy strategy

Talked through the actual options for getting code onto the droplet — git-clone-and-build-on-droplet, CI→registry with the droplet just pulling an image, a remote Docker build over an SSH context, and rsync — before picking one. Landed on **GitHub Actions → GHCR, droplet does a manual pull**. Explicitly *not* full auto-deploy: that would mean either a production-capable SSH key sitting in GitHub Actions secrets, or a poller service babysitting the droplet — both more than a one-service personal project needs right now. Added `push-service/Dockerfile`, `.dockerignore`, and `.github/workflows/push-service.yml` (builds and pushes `ghcr.io/bystrek/push-service:latest` + `:<sha>` on every push to `push-service/**`). Verified the image builds and runs correctly with a local `docker build`/`docker run` before trusting CI with it.

### GHCR pull auth

Tried a **fine-grained** GitHub PAT first for the droplet's pull auth, since it's the more modern/scoped option — turned out fine-grained tokens don't expose a Packages permission at all for org-owned repos (confirmed by trying to create one, not just by reading about it). Fell back to a classic PAT with `read:packages` scope.

Getting the token onto the droplet raised a real concern: a naive `scp` of the user's local token file would've overwritten the droplet's existing `.env` (wiping `CF_API_TOKEN`), and having Claude read the token file directly would put the secret value into the conversation. Solved both: piped just the matching line from the local file through `ssh ... 'cat >> ~/bystrek/.env'` (value flows local file → SSH stdin → remote append, never appears in anything Claude reads), and later ran `docker login` on the droplet by sourcing the `.env` and piping into `--password-stdin` remotely — same principle, the raw token is never echoed anywhere visible.

### Wiring into the droplet

Added `push-service` to the droplet's `docker-compose.yml` (pulling the GHCR image, own SQLite volume) and initially routed `/push/*` through Caddy path-based routing alongside `open-webui`. Verified live over Tailscale.

### The Open WebUI routing problem

Asked "how do I actually subscribe on my phone, given root is Open WebUI?" — turned into a real design problem, not a detail. iOS only exposes the Web Push APIs to a **home-screen-installed** app, and permission is tied to *which installed app* requested it — not just the origin. A separate `/push/` page installed as its own icon would recreate exactly the "two icons" problem day three's plan was designed around avoiding (see the ntfy rejection above).

Considered moving Open WebUI to `/openwebui` to free up root for a combined entry point. Checked first rather than risk it: Open WebUI (SvelteKit) has a history of broken subpath deployment (hardcoded root-relative asset/API paths), with `WEBUI_BASE_URL`/`PUBLIC_BASE_PATH` support added only recently and still showing open bug reports. Breaking the chat UI already in daily use, to test a feature not yet in use, was a bad trade — didn't do it.

Landed on the pragmatic option instead: **push-service now owns `bystrek.dev` root outright**, serving a minimal subscribe-only page (cream/wine, pulled from `brand/icon.svg`'s actual fill colors — `#F3E7D3`/`#591622` — rather than guessing) with an "Enable notifications" button. Open WebUI is disabled at the routing level — its container keeps running on the droplet, unrouted, so re-enabling it later is a Caddyfile change, not a redeploy. Moved `sw.js` from `/push/sw.js` to `/sw.js` so its default service-worker scope covers the whole origin. Caddyfile simplified from two `handle` blocks down to a single `reverse_proxy push-service:8787`. The real fix — subscribe flow living *inside* the same installed app as the chat, likely via response injection at the Caddy layer rather than a subpath move — is deferred to day four.

### Problems hit along the way

- Compose didn't recreate the `caddy` container after the second Caddyfile edit (only the bind-mounted file changed, not the service definition in `docker-compose.yml`) — same class of issue as day two. Fixed the same way: explicit `docker compose exec caddy caddy reload`.
- Caddy flagged the hand-written Caddyfile as not `caddy fmt`-clean (tabs vs. spaces) — ran `caddy fmt --overwrite` inside the running container to fix it in place.
