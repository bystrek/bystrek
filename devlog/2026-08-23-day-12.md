# Day Twelve — bystrek.dev

**Date:** 2026-08-23
**Goal:** Item 10 from `whats-next.md` — close the `update-user` image size gap — then a roadmap brainstorm for what ships as MVP vs. gets deferred.

## What we decided

**Enforce the limit in a `databaseHooks.user.update.before` hook, not a new endpoint or a body-parser change.** `/api/auth` is mounted ahead of Nest's `express.json()` (needed because better-auth wants the raw request body), so the app's normal 100KB body limit never applies to it, and `users.image` is a plain unbounded `text` column. Rather than adding a separate size-checking middleware in front of `/api/auth` or a custom controller, better-auth already exposes a lifecycle hook that runs before any user row write and can throw to reject it — same "reuse the tool already wired in" reasoning as the profile work on day 11. Threw a `better-auth` `APIError('PAYLOAD_TOO_LARGE', …)` so a bad payload gets a real 413, not a silent no-op.

**Cap on the base64 string length (~280,000 chars), not the decoded byte count.** Decoding to check the real byte size would mean base64-decoding untrusted input on every update just to reject most of it — cheaper to bound the string length directly. 280,000 chars decodes to ~200KB, comfortably above the UI's actual output (a 256px JPEG at quality 0.8, tens of KB) so legitimate uploads never get near the limit, but far below "arbitrary" so the gap is actually closed.

## What we actually built

- `api/src/auth/auth.config.ts`: `MAX_IMAGE_BASE64_LENGTH` constant + a `databaseHooks.user.update.before` hook rejecting an oversized `user.image` string.
- `api/test/integration/profile.integration.spec.ts`: new case posting a 300,000-char image to `update-user`, asserting 413.

## Continuation: roadmap restructure, household removal, and the Proton→Infomaniak migration (2nd session, same day)

**Goal:** Docs-only session. Rename `whats-next.md` to `roadmap.md`, restructure it, define an MVP, and settle the calendar-source question that's been blocking the calendar vertical slice.

### What we decided

**Drop the `households` table entirely.** Originally built as "multi-user via household," but devlog day-04 already called this a "single-household app" — the cardinality was always meant to be exactly 1 household per deployment, never many. That reframes the question: it's not about multi-tenancy (never needed), it's about whether a grouping table with a guaranteed cardinality of 1 earns its FK/cascade/join overhead. The deciding argument: bystrek's encryption model is tier-2 only (app-level AES-256-GCM, not zero-knowledge — see `architecture.md`), explicitly so the LLM can read everything. If a second household were ever hosted, sharing one DB between two families' medical records behind app-level `household_id` scoping would be a strictly worse security boundary than just standing up a second droplet+DB for them. So even in the hypothetical future, `households` isn't the right tool for that job — infra-level separation is. Conclusion: multi-*user* stays (via `users` directly), multi-*household* goes. `owner_id`/`visibility` collapses from `private`/`household` to `private`/`shared`.

**MVP defined, roadmap split into MVP / Post-MVP.** MVP: drop household, calendar source decision, calendar CRUD via chat (incl. recurring events), an agenda view, a daily digest push. Post-MVP: notes/research/medical/nutrition/gym domains, broader proactive nudging, Signal Forms migration. Reasoning for what's actually MVP vs. later wasn't really debated — the user came in with this shape already decided from their own thinking outside the session.

**RabbitMQ, not pg-boss or BullMQ, for the daily digest / future proactive nudging.** User wants a message-queue learning experience transferable to work, which ruled out pg-boss (Postgres-backed, zero new infra, but "a nice polling library" not "a message queue"). Between BullMQ+Redis and RabbitMQ: BullMQ is a good developer-ergonomics library on top of Redis, but less differentiated as "message queue experience" specifically; Kafka was considered and rejected — it's an event-streaming log (partitions/consumer groups/offsets), a different paradigm than "run this job daily," and operationally heavier than a single droplet needs. RabbitMQ (AMQP: exchanges, routing keys, ack/nack, dead-letter queues) matches the actual workload shape (discrete task → discrete action) and is the most commonly-referenced "message queue" in job postings. Added to `architecture.md`'s Layering section as a decided component (scheduler → RabbitMQ → worker → backend API/push).

**Calendar source: dropped Proton entirely, migrating to Infomaniak kSuite (kMail + kCalendar + kDrive).** This was the big one, and it went through several rounds:

1. Confirmed Proton Calendar has zero CalDAV support, officially, by design — its zero-access E2E encryption model can't coexist with CalDAV's server-side read/edit protocol. Only official option is a read-only shared-link ICS subscription (4-8hr propagation delay, no write-back).
2. Confirmed there's no official Proton API for third parties at all, for any product. `ProtonMail/go-proton-api` is a real Proton AG-maintained Go library that does include calendar endpoints, but it's explicitly internal tooling ("not actively looking for contributors," tests need live account creds) — not a supported public surface. Every unofficial bridge (Ferroxide, `proton-calendar-sync`) is reverse-engineered against that same unversioned private API.
3. Evaluated self-hosting Ferroxide as a "keep everything in Proton" compromise — rejected specifically because its own docs flag recurring-event handling as "still rough," which collides directly with the MVP's explicit recurring-events requirement. `proton-calendar-sync` was also ruled out as macOS-only (single commit, 1 star) — not deployable on the Linux droplet.
4. Given the user was still early in a Proton migration (not deeply invested), reframed the question from "how do we bridge to Proton" to "should Proton be the destination at all." Surveyed European/privacy-focused full-suite alternatives: Mailfence, mailbox.org, Kolab Now, Posteo, Infomaniak kSuite.
5. **mailbox.org ruled out** despite being a common privacy-community recommendation: their own Privacy Guides forum has an active "Remove mailbox.org" thread citing improperly implemented SPF/DKIM/DMARC on custom domains and unencrypted sent mail (only inbound is PGP-encrypted) — a real, sourced red flag, not just "less popular."
6. **Infomaniak kSuite chosen**: native documented CalDAV/CardDAV (confirmed working with Apple Calendar/Thunderbird/Outlook), broadest suite match to what Proton offered (kMail/kCalendar/kDrive/kMeet/kChat/Euria AI, real-time OnlyOffice-based doc collaboration), Swiss-hosted, no data monetization, consistently well-reviewed with no comparable red flags found. Free default domains: `@ik.me`/`@ikmail.com`/`@etik.com`, or bring a custom domain.
7. VPN and password-manager gaps (Proton bundles both) turned out to be non-issues — user already has Surfshark (family codes) and Bitwarden, both untouched by this migration.
8. **2FA/authenticator**: Proton Authenticator has no kSuite equivalent (Infomaniak's own "kAuth" app is only for logging into Infomaniak's *own* services, not a general TOTP vault). Considered 2FAS and Ente Auth (both open-source, cross-platform; Ente is additionally self-hostable, consistent with the project's self-hosting ethos, audited by Cure53/Symbolic Software) and Aegis (rejected — Android-only, user is on iOS). User ultimately picked **Bitwarden Authenticator** — a genuinely standalone, free, open-source, no-account-required app Bitwarden ships separately from the password manager (not the vault-integrated TOTP field, which was correctly flagged as a bad idea for anything important since it puts both factors in one breach blast radius). Chosen for zero-new-vendor convenience over the other options' marginally better sync/self-host story.
9. Considered and explicitly rejected using Infomaniak as bystrek's own OIDC identity provider (Infomaniak does support real OAuth2/OIDC "Sign in with Infomaniak," and `better-auth` has a generic-OIDC plugin, so it's technically live). Rejected because `architecture.md`'s Auth section already deliberately chose self-hosted `better-auth` specifically to avoid third-party IdP dependency for the app gating the most sensitive data, and because household members would need their own Infomaniak accounts just to log into bystrek — a net-worse tradeoff for a small household app with negligible SSO payoff. This was raised as a tangent/curiosity, not something being planned.

Practical migration notes captured during the session, not architecture: Apple ID does *not* require using `@icloud.com` mail — Proton can stay the actual inbox even where iCloud was briefly considered, though this became moot once Infomaniak was chosen outright. Calendar invites sent to a Proton/Infomaniak address land in that provider's own calendar via ICS auto-import, not automatically in whatever calendar bystrek reads — a manual step is needed for third-party invites, flagged as a known limitation rather than a blocker.

## Continuation: calendar vertical slice plan (4th session, same day)

**Goal:** Plan the next PR — CalDAV sync connector + calendar CRUD chat tool, the first two roadmap items in the calendar vertical slice.

### What we decided

**Connector (CalDAV sync) and chat tool (calendar CRUD) ship together, one PR, not split.** The connector has no caller until the tool exists — landing it alone means dead code sitting unused for a PR cycle, and the two aren't independently testable: the tool can't work without the connector. The roadmap already frames "calendar CRUD via chat" as one deliverable. Agenda view and the RabbitMQ-backed daily digest stay separate PRs — agenda view is pure UI reading the same service, and the digest needs its own distinct infra (RabbitMQ wiring) that doesn't belong bundled in.

**Credentials: separate `calendar_credentials` table, not columns on `users`.** The Infomaniak app-specific password is per-user data, not a deployment secret — it doesn't fit the droplet `.env` pattern (that's for secrets the app itself needs, shared across all users, like the Resend key or VAPID keys). A dedicated table (rather than extra `users` columns) keeps `users` from accumulating unrelated fields and leaves room to grow (CalDAV URL, calendar name, and potentially more integrations later) without another schema churn.

**Reuse the existing `field-encryption` wrapper (`api/src/crypto/field-encryption.ts`), not a new encryption mechanism.** Initially mis-stated this as something still to be built — checked `schema.ts` and confirmed `messages.content` already uses it. `calendar_credentials`' password/URL fields are just another consumer of the same AES-256-GCM wrapper, no new crypto code needed.

**UI-editable via profile page, not baked into deploy config.** Since it's per-user data (not a shared app secret), it needs a normal settings surface — a new section on the existing profile page to set/edit the app-specific password, CalDAV URL, and calendar name — rather than living in `.env` or being set only via seed/migration.

**No client-side recurrence expansion.** Partway through planning the connector, caught myself reaching for `ical.js` to expand `RRULE` into individual occurrences for the (later) agenda view — wrong: Infomaniak is the CalDAV server of record, and CalDAV's `calendar-query` REPORT with a time-range filter already returns server-expanded occurrences, same as what iOS Calendar relies on. `tsdav`'s `fetchCalendarObjects` exposes this directly via `{ timeRange, expand: true }`. `ical.js` is still used, but only for building/parsing the `RRULE` field's RFC 5545 syntax when creating/editing an event — not for expanding it. Also worth noting: iCalendar/CalDAV are vendor-neutral IETF standards (RFC 5545/4791), not Apple-specific, despite Apple's involvement in authoring CalDAV — using them isn't a vendor lock-in tradeoff, it's what makes the "swap CalDAV provider later" story in `docs/architecture.md` actually work.

**`ChatTool.handler` gained a `userId` parameter.** `CHAT_TOOLS` was a static, request-independent array (`chat.tools.ts`); calendar tools need to know *whose* calendar to act on, which the existing handler signature (`(input) => Promise<unknown>`) had no way to express. Changed the interface to `(input, userId) => Promise<unknown>` and `ChatService`'s dispatch loop now passes `userId` through — the only call site that needed updating. `CHAT_TOOLS` itself changed from a static `useValue` to a `useFactory` that combines per-domain tool arrays (`CALENDAR_TOOLS` from `calendar.module.ts`, exported and injected into `chat.module.ts`) — the pattern later domains (notes, etc.) will follow rather than editing a shared tools file directly.

**Calendar tool handlers never throw.** Each of the four tools (`list_calendar_events`, `create_calendar_event`, `update_calendar_event`, `delete_calendar_event`) wraps its work in a `safely()` helper that catches any error (no calendar connected, event not found, upstream CalDAV failure) and returns `{ error: message }` as the tool_result instead. Lets Claude see the failure and explain it or ask the user to fix setup, rather than the whole chat request 500ing on a tool failure.

**Blank password on update means "keep the existing one," not "clear it."** The profile form never echoes the stored password back (`getSummary()` only returns `configured`/`caldavUrl`/`username`/`calendarName`), so a user editing just the calendar name with the password field left blank would otherwise overwrite the encrypted password with ciphertext of an empty string. `CalendarCredentialsService.set()` now reuses the existing encrypted password when the incoming one is empty, and 400s if there's no existing row to fall back to (first-time setup requires a password).

## Continuation: live verification against the real Infomaniak account (5th session, same day)

**Goal:** Verify the calendar connector actually works against the user's real Infomaniak account, not just mocks/unit tests — the one gap flagged at the end of the previous session.

A one-off script (`api/scratch-live-caldav-test.ts`, deleted immediately after the run, matching the day-12-session-4 pattern for the scratch test-user script) was the right tool: prove the wiring once, by hand, then throw it away.

## Continuation: end-to-end chat tool-call verification finds a real bug (6th session, same day)

**Goal:** Verify the calendar tools work through an actual chat conversation — Claude deciding to call `list_calendar_events`/etc. and the tool_use round-trip completing — not just the connector in isolation (session 5) or mocked tool tests (session 4).

### What we decided

**Give Claude the actual current date/time in the system prompt, computed per request.** First live test — a real `POST /chat` asking "what's on my calendar in the next 30 days" — returned 0 events despite the same live account having 19 (confirmed identical in session 5). Root cause, found by temporarily logging the tool's raw input: Claude requested the range `2024-12-19` to `2025-01-18`, guessing "now" from training-data recency instead of the real date (2026-08-23). Every relative-time query (today/this week/next N days) was silently broken — not a connector bug, a missing-context bug. Fixed by computing a per-request system prompt (`buildSystemPrompt()` in `chat.service.ts`) carrying the current date/time formatted for `Europe/Warsaw` plus the raw ISO instant, with an explicit instruction not to guess it from training data. Timezone is a fixed constant, not a per-user setting, since there's currently exactly one user — noted as revisit-later, matching this session's "not blocking" framing for working-hours/default-calendar-name context in the roadmap.

**Fix verified by rerunning the same failing chat message, not just re-running unit tests.** Unit tests wouldn't have caught this at all — `buildSystemPrompt()`'s date-injection logic has no failure mode a mock can exercise; the bug only exists in the interaction between "no date context" and a real model's actual guess. Retested the identical `POST /chat` call end-to-end: same account, same question, now correctly returns 19 events with `list_calendar_events` cited as the tool used.

### What we actually built

- `api/src/chat/chat.service.ts`: `SYSTEM_PROMPT` constant replaced with `buildSystemPrompt()`, called fresh on every request; adds current date/time (`Intl.DateTimeFormat`, `Europe/Warsaw`) and the raw ISO instant, with an explicit "don't guess this from training data" instruction and a directive to use ISO 8601 in that timezone for tool inputs.

### Problems hit along the way (and the actual fixes)

**First live chat test silently returned 0 events instead of erroring.** Nothing in the stack was broken — `list_calendar_events`'s `safely()` wrapper correctly returned an empty array for an (accidentally) valid-but-wrong date range, exactly as designed. ## Continuation: Copilot review finds a real write-safety gap (7th session, same day)

**Goal:** Run `/copilot-review` against PR #13, verify each finding against the actual code (not trust it blindly), fix what's real.

### What we decided

**`gh pr edit --add-reviewer @copilot` silently no-ops on the first attempt, but isn't actually broken — just slow.** First run: the command reported success, `requested_reviewers` stayed empty, ~4.5 minutes of polling found no review, concluded Copilot code review wasn't enabled for this repo/plan. Re-running `/copilot-review` later in the same session found 11 real, substantive unresolved comments — the review had landed after all, just past the skill's 3-minute polling budget. Lesson for next time: a `gh pr edit --add-reviewer @copilot` that "succeeds" with an empty `requested_reviewers` isn't necessarily a dead end — worth a longer wait or a manual re-check via the GraphQL `reviewThreads` query before concluding it's unavailable.

**Confirmation gate for mutating calendar tools, not just a system-prompt hint.** The single most consequential finding: `docs/architecture.md`'s Write safety section requires "explicit confirmation for sensitive writes rather than silent auto-execution," and the shipped `create_calendar_event`/`update_calendar_event`/`delete_calendar_event` tools executed immediately on a model decision — a real architecture violation, not a nitpick, and exactly the kind of thing a prompt-injected calendar event description could exploit (get the model to "confirm" its own destructive action in the same turn). User's call: fix it now rather than defer. Design chosen — **propose → confirm, enforced server-side, not just via a system-prompt instruction**: mutating tools become `propose_create_calendar_event`/`propose_update_calendar_event`/`propose_delete_calendar_event`, which stage the action (`PendingCalendarActions`, in-memory, 10-minute TTL, keyed by a random confirmation id) and return a human-readable preview — no mutation yet. A new `confirm_calendar_action` tool executes a staged action by id, but `PendingCalendarActions.take()` refuses to hand it back if the confirm call's `requestId` matches the propose call's `requestId`. `ChatService.reply()` now generates one `requestId` (`randomUUID()`) per user message, shared across every tool-call iteration in that single request — so confirming genuinely requires a separate human turn (a new chat message), not just a second tool call within the same model reply. A prompt-only "please ask before executing" instruction wouldn't have survived an adversarial or hallucinated model decision; this does, structurally. `list_calendar_events` (read-only) is untouched — the write-safety requirement is specifically about writes.

**SSRF/plaintext-HTTP validation on `caldavUrl`, scoped to the actual threat model.** Copilot correctly flagged that `caldavUrl` was stored and used as a server-side request target (Basic-auth password included) with zero validation — a user could point it at `http://169.254.169.254/` or any internal host. User deferred the scope call; decided on basic defense-in-depth (require HTTPS, reject a hardcoded list of private/link-local hostname patterns) rather than full SSRF hardening (DNS-rebinding-safe redirect handling, live resolution checks) — proportionate to an invite-only household app where every account holder is already a trusted invited user, not a hardened multi-tenant boundary. New `caldav-url.ts` (`assertSafeCaldavUrl`), enforced at both store-time (`CalendarCredentialsService.set`) and use-time (`CalendarService.connect`, defense-in-depth against any row written before this check existed).

**UID lookup fixed to match the real iCalendar UID, not the resource filename.** Confirmed real bug: `findObjectByUid` matched `${uid}.ics` against the resource URL, which only holds for events this service created itself — an event from any other CalDAV client could have an arbitrary filename, so update/delete would silently 404 it. Fixed to parse each candidate object's actual `UID` field and compare that. Caught by a new test that mocks `tsdav` directly (`calendar.service.spec.ts`) with a fake object whose filename deliberately doesn't match its UID — exactly the gap Copilot pointed out ("the live round-trip only exercises events created here").

### Problems hit along the way (and the actual fixes)

**A dynamic `import()` inside `calendar.service.spec.ts` resolves to `any` under this project's lint setup**, cascading `no-unsafe-*` errors through everything derived from it. Root cause: `eslint.config.mjs`'s `languageOptions.sourceType: 'commonjs'` vs. `tsconfig.json`'s `module: 'nodenext'` — a mismatch between what the ESLint parser assumes and what the type checker actually resolves, specific to dynamic-import expressions (an explicit type annotation on the assignment target didn't clear it, since the rule reads the *source* expression's inferred type, not the target). Most of the cascade was self-inflicted, though: an earlier draft typed a mock-loader helper's parameter as `ReturnType<typeof mock>` (an overloaded generic referenced without invocation, itself resolving to `any`), which explains most of the ~30 errors along the way. Rewriting with concrete local interfaces for the fake CalDAV client (no generic `mock` types crossing function boundaries) fixed all but the one genuine dynamic-import case, which got a single scoped `eslint-disable-next-line` — the repo's first, kept to one line with a comment explaining why it's not a real unsafe operation.
