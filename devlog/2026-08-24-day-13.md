# Day Thirteen — bystrek.dev

**Date:** 2026-08-24
**Goal:** Fix issue #17 — calendar event create/update silently shifted by the server-vs-user timezone delta when the model omits a UTC offset.

## What we decided

**Reverse `zoned-time.ts`'s existing formatter into a parser, rather than validating/rejecting offset-less input.** The read path (`formatZonedIso`, day 12 session 12) already solves the equivalent problem for tool *output* — never make the model do timezone math, hand it an unambiguous already-localized string. The write path never got the same treatment: `propose_create_calendar_event`/`propose_update_calendar_event`/`list_calendar_events` parsed `start`/`end` via bare `new Date(...)`, which interprets an offset-less string in the server process's local timezone (UTC, since no `TZ` is set anywhere in the container) rather than the user's configured one — exactly the reported 2-hour Warsaw shift. Rejecting offset-less input outright was the other option raised in the issue, but discarded: the system prompt only *asks* the model for an offset, so rejecting would trade a silent wrong answer for a frequent hard failure. Parsing defensively (treat a bare string as wall-clock time in `ctx.timezone`, still respect an explicit offset when present) fixes the common case without adding a new failure mode for a well-behaved model.

**Offset detection stays a simple suffix check (`Z` or `±HH:MM`), not a full ISO 8601 parser.** Tool inputs are model-generated, not arbitrary user text — the two shapes actually seen are "bare local-looking string" and "string with an explicit offset," so a regex suffix check is enough to route correctly without pulling in a date library.

## What we actually built

- `api/src/calendar/zoned-time.ts`: `parseZonedIso(input, timeZone)` — new, the inverse of `formatZonedIso`. Respects an explicit offset (`Z`/`±HH:MM`) via `new Date(...)`; otherwise parses the string as wall-clock components and converts to UTC using the same DST-correct offset technique `formatZonedIso` already used (factored the shared offset math into `zoneOffsetMinutes`).
- `api/src/calendar/calendar.tools.ts`: `list_calendar_events`, `propose_create_calendar_event`, `propose_update_calendar_event` now call `parseZonedIso(str, ctx.timezone)` instead of `new Date(str)`.
- `api/src/calendar/zoned-time.spec.ts`: new `parseZonedIso` cases — bare datetime in summer/winter Warsaw (DST), explicit offset and `Z` both take precedence over the timezone argument, round-trip with `formatZonedIso`, clear error on unparseable input.
- `api/src/calendar/calendar.tools.spec.ts`: new regression case reproducing the issue's exact repro shape (offset-less `19:00` proposed and confirmed, asserts the resulting `createEvent` call carries the correctly-shifted UTC instant, not a UTC-as-local misread).

## Problems hit along the way (and the actual fixes)

**Wrapping `propose_create_calendar_event`'s handler in the existing `safely()` error guard (to catch `parseZonedIso` throwing on malformed input) tripped `@typescript-eslint/require-await`** — the handler's work is fully synchronous, so an `async () => {...}` body with no `await` inside is flagged. Fixed by loosening `safely`'s signature from `fn: () => Promise<T>` to `fn: () => T | Promise<T>` (it already does `await fn()` internally, which works fine on a non-promise value) and dropping the unnecessary `async` from the inner function, rather than adding a pointless `await Promise.resolve()` just to satisfy the rule.
