# Day Thirteen — bystrek.dev

**Date:** 2026-08-24
**Goal:** Fix issue #17 — calendar event create/update silently shifted by the server-vs-user timezone delta when the model omits a UTC offset.

## What we decided

**Reverse `zoned-time.ts`'s existing formatter into a parser, rather than validating/rejecting offset-less input.** The read path (`formatZonedIso`, day 12 session 12) already solves the equivalent problem for tool *output* — never make the model do timezone math, hand it an unambiguous already-localized string. The write path never got the same treatment: `propose_create_calendar_event`/`propose_update_calendar_event`/`list_calendar_events` parsed `start`/`end` via bare `new Date(...)`, which interprets an offset-less string in the server process's local timezone (UTC, since no `TZ` is set anywhere in the container) rather than the user's configured one — exactly the reported 2-hour Warsaw shift. Rejecting offset-less input outright was the other option raised in the issue, but discarded: the system prompt only *asks* the model for an offset, so rejecting would trade a silent wrong answer for a frequent hard failure. Parsing defensively (treat a bare string as wall-clock time in `ctx.timezone`, still respect an explicit offset when present) fixes the common case without adding a new failure mode for a well-behaved model.

**Offset detection stays a simple suffix check (`Z` or `±HH:MM`), not a full ISO 8601 parser.** Tool inputs are model-generated, not arbitrary user text — the two shapes actually seen are "bare local-looking string" and "string with an explicit offset," so a regex suffix check is enough to route correctly without pulling in a date library.

## What we actually built

- `api/src/calendar/zoned-time.ts`: `parseZonedIso(input, timeZone)` — new, the inverse of `formatZonedIso`. Respects an explicit offset (`Z`/`±HH:MM`) via `new Date(...)`; otherwise parses the string as wall-clock components and converts to UTC using the same DST-correct offset technique `formatZonedIso` already used (factored the shared offset math into `zoneOffsetMinutes`).
- `api/src/calendar/calendar.tools.ts`: `list_calendar_events`, `propose_create_calendar_event`, `propose_update_calendar_event` now call `parseZonedIso(str, ctx.timezone)` instead of `new Date(str)`.
- `api/src/calendar/zoned-time.spec.ts`: new `parseZonedIso` cases — bare datetime in summer/winter Warsaw (DST), explicit offset and `Z` both take precedence over the timezone argument, round-trip with `formatZonedIso`, clear error on unparseable input.
- `api/src/calendar/calendar.tools.spec.ts`: new regression case reproducing the issue's exact repro shape (offset-less `19:00` proposed and confirmed, asserts the resulting `createEvent` call carries the correctly-shifted UTC instant, not a UTC-as-local misread).

## Problems hit along the way (and the actual fixes)

**Wrapping `propose_create_calendar_event`'s handler in the existing `safely()` error guard (to catch `parseZonedIso` throwing on malformed input) tripped `@typescript-eslint/require-await`** — the handler's work is fully synchronous, so an `async () => {...}` body with no `await` inside is flagged. Fixed by loosening `safely`'s signature from `fn: () => Promise<T>` to `fn: () => T | Promise<T>` (it already does `await fn()` internally, which works fine on a non-promise value) and dropping the unnecessary `async` from the inner function, rather than adding a pointless `await Promise.resolve()` just to satisfy the rule.

## Current state

Issue #17 fixed: calendar event create/update no longer silently shifts by the server-vs-user timezone delta when the model omits a UTC offset. `bun run build`/`test`/`test:integration` all green, lint at the same 14-error/37-warning baseline as day 12 (no new errors — the one introduced mid-session was fixed, not left). Not yet verified against a real chat conversation or the live Infomaniak account. Opened as PR #19, closing #17. Issue #18 ("next Tuesday" weekday math) remains, as does agenda view / the RabbitMQ daily digest (both explicitly deferred, per user, to their own future PRs — not part of this session's scope).

## Continuation: replace hand-rolled offset/DST math with native Temporal (2nd session, same day)

**Goal:** User asked how much a Temporal-aware runtime would simplify `zoned-time.ts`, given the offset arithmetic there just produced #17. Follow-up on whether that's actually available now, and if so, use it.

### What we decided

**Bun ships `Temporal` natively as of 1.4.0 (released today, 2026-08-24), not just merged-and-unreleased.** `oven-sh/bun#32978` flips `JSC::Options::useTemporal()` on by default — JavaScriptCore already had a 100%-test262-passing implementation hidden behind a runtime flag. Confirmed live (not from the PR description alone): installed `bun@1.4.0` via `npm install bun@1.4.0` into a scratch dir (kept separate from the globally-installed `1.3.14` so as not to touch the user's toolchain mid-investigation) and ran `Temporal.Now.zonedDateTimeISO('Europe/Warsaw')` — worked, correct DST-aware output. This is a genuinely different answer from the first pass at this question: MDN's Temporal page (still "not Baseline") led to a too-broad "not shipped anywhere stable" conclusion that didn't hold once the actual PR was checked — Bun is ahead of browsers/Node here, and blending "is it standardized" with "is it available in our runtime" was a real reasoning slip, called out directly by the user and worth remembering as a distinct pair of questions to keep separate next time.

**Rewrite `zoned-time.ts` against native `Temporal` rather than the `@js-temporal/polyfill` package.** Scoped this to the one file that actually does timezone arithmetic — `pending-actions.ts`'s `Date.now()` TTL bookkeeping and `schema.ts`'s `$onUpdate(() => new Date())` timestamp defaults have no offset/DST logic to simplify, so they're untouched. With native Temporal confirmed available in the runtime we already ship, a polyfill dependency (even dev-only) would be pure overhead — same API surface, no benefit.

**First pass hand-wrote an ambient `declare global` block, on the belief no `@types` package covers Temporal — user pushed back to re-check, and that belief was wrong.** Direct research (not memory) on a second pass found `typescript@6.0.3` (latest stable, released) ships an official `lib.esnext.temporal.d.ts` — the real spec-accurate ambient `declare namespace Temporal {...}`, verified by downloading and inspecting the actual npm tarball. It's opt-in, not bundled into `target: esnext`'s default lib set, but pullable via a single `/// <reference lib="esnext.temporal" />` directive in `zoned-time.ts` — no `compilerOptions.lib` array surgery needed. This meant bumping the `typescript` devDependency from `^5.7.3` to `^6.0.3` rather than keeping the hand-rolled block. Checked compatibility first: `typescript-eslint`'s installed `8.20.0` peers on `typescript: >=4.8.4 <5.8.0` (excludes 6.0.3), but the newer `8.66.0`/`8.68.0` (already satisfied by the repo's existing `^8.20.0` range) peers on `<6.1.0` — so a plain `bun install` refresh picked up a compatible version with no `package.json` edit needed there. `@nestjs/cli` doesn't peer on `typescript` at all (build goes through `swc`).

### What we actually built

- `api/src/calendar/zoned-time.ts`: rewritten against native `Temporal`, typed via the official `esnext.temporal` lib (one `/// <reference lib="esnext.temporal" />` line) instead of a hand-rolled ambient block. `formatZonedIso`/`parseZonedIso`'s hand-rolled offset math (`zoneOffsetMinutes`, `formatOffset`, the `Intl.DateTimeFormat` formatter cache) is gone — replaced by `Temporal.Instant.fromEpochMilliseconds(...).toZonedDateTimeISO(timeZone).toString(...)` and `Temporal.PlainDateTime.from(...).toZonedDateTime(timeZone)`. `assertValidTimeZone` now probes via `Temporal` instead of `Intl.DateTimeFormat`. File shrank from ~120 lines to ~55.
- `api/package.json`: `typescript` `^5.7.3` → `^6.0.3`.
- `api/tsconfig.json`: `baseUrl` removed (confirmed unused — no non-relative imports rely on it — and TS 6.0 now hard-errors on it by default, `TS5101`, rather than just warning); `"types": ["bun-types"]` added explicitly (TS 6.0's `nodenext` resolution stopped auto-discovering `@types/bun` the way 5.7 did — see Problems below).
- `api/tsconfig.build.json`: gained its own `"rootDir": "./src"` (TS 6.0's `TS5011` now requires it explicitly for the build-only config, which already excludes `test/`/specs/`drizzle.config.ts` so this is unambiguous there).
- `ui/package.json`: `packageManager` bumped `bun@1.3.14` → `bun@1.4.0`, for local-toolchain consistency (`ng build`/`ng test` confirmed clean under 1.4.0; `ui` has no Temporal-relevant code or TS version change, this is just the pin).
- No Dockerfile/CI change needed: `oven/bun:1` (both Dockerfiles) and `oven-sh/setup-bun@v2` (CI, no `bun-version` pin) already float to the latest 1.x, so 1.4.0 is picked up automatically on the next build.

### Problems hit along the way (and the actual fixes)

**Naively adding `"rootDir": "./src"` to the shared `tsconfig.json` (to fix the build's `TS5011`) broke `bun run lint` with 603 new errors, every one "type could not be resolved" on `bun:test`'s `describe`/`it`/`expect`, project-wide.** First hypothesis (wrong, but plausible-looking): a `typescript@6.0.3`-vs-`typescript-eslint` incompatibility specifically around `bun:test`'s ambient module resolution under ESLint's `projectService`. Investigated properly rather than accepting that: isolated variables one at a time (reverted the `rootDir` edit alone, kept only the TS bump — same 603 errors, so `rootDir` wasn't it) and ran `tsc --noEmit` directly against the *unmodified* `tsconfig.json` to see the real, non-ESLint-filtered diagnostic. That surfaced the actual root cause: `TS5101` (`baseUrl` deprecated, now a hard **error** by default in TS 6.0, not a warning) aborts `tsc`'s program construction entirely before it checks a single file — and ESLint's `projectService`, hitting that same failed program build, silently falls back to "no type info" for every file rather than surfacing the config error itself. One root cause (the pre-existing, already-unused `baseUrl`), not a distributed bug. Removing `baseUrl` (confirmed safe — grepped for any non-relative import that would've depended on it, found none) immediately dropped it to a handful of real, specific `TS2307: Cannot find module 'bun:test'` errors — which turned out to be a second, genuine, narrower issue: TS 6.0's `nodenext` resolution needs `"types": ["bun-types"]` stated explicitly now, where 5.7 auto-discovered it. Fixed both, back to the exact 14-error/37-warning baseline. Lesson: when a version bump produces an implausibly large, uniform error spray, look for one shared root cause upstream of the individual diagnostics (a failed program/config, not per-file breakage) before assuming a deep tool incompatibility.

**Local dev `bun` is still `1.3.14` — didn't touch the global install.** All verification this session (`build`/`test`/`test:integration`/`lint` for `api`, `build`/`test` for `ui`) ran against a scratch-installed `bun@1.4.0` binary (`npm install bun@1.4.0 --no-save` into the scratchpad), not the user's global `bun`. The user's global install still needs a real `bun upgrade` (or reinstall) before `bun run build`/`test` work locally without the scratch binary — flagged, not done automatically, since it changes the user's actual toolchain.

### Current state

`zoned-time.ts` rewritten against native `Temporal` (Bun 1.4.0) and typed via TypeScript 6.0.3's official `esnext.temporal` lib, same public API (`assertValidTimeZone`/`formatZonedIso`/`parseZonedIso`), same test suite passing unchanged — confirms the output format didn't shift. `bun run build`/`test`/`test:integration`/`lint` (api) and `ng build`/`ng test` (ui) all green under the scratch `bun@1.4.0` binary; lint back at the exact 14-error/37-warning baseline. Not yet pushed — this continues PR #19 (same underlying file as the #17 fix). Still open: the user's global `bun` needs manually upgrading to actually run these `bun run ...` scripts locally without the scratch workaround; three pre-existing `tsc`-only type errors surfaced during investigation (`calendar.service.spec.ts`'s self-import, two `ToolContext`/`InputSchema` shape gaps in test files) were never actually caught before (specs are excluded from `nest build`, and `bun test` doesn't type-check) — left as-is, out of scope for this session, worth a follow-up to add a real `tsc --noEmit` check to CI so they don't stay invisible; issue #18 and the deferred agenda-view/daily-digest items remain untouched.

## Continuation: visual direction for a UI overhaul (3rd session, same day)

**Goal:** current UI reads as "hodge-podge, amateurish, obviously stitched-together pages." User wants a deliberate visual direction, described only in trend terms: bold fonts, high contrast, no border-radius, no box-shadow, no gradients.

### What we decided

**Direction is neo-brutalism** (stark grids, hard edges, borders instead of shadows for depth, heavy type) — matches the description exactly. Narrowed with three quick answers: undecided on color strategy but wants to prepare multiple CSS-themed variants to compare side by side; okay with thick borders standing in for shadow-based depth; UI should stay minimal/content-light rather than dashboard-dense, matching bystrek's actual current surface (subscribe + chat).

**No design-system library for now — hand-roll CSS custom-property tokens directly on Angular components (option C), not the previously-logged [[project_design_system_candidates|Lion pick]] and not the newly-found `ng-brutalism`.** Researched both real alternatives before deciding, rather than picking on vibes:
- **Lion + hand-rolled skin (option B):** the original plan from a few days ago. Stable, actively-maintained, unstyled primitives — but "too much work" per the user, and brutalism doesn't obviously need Lion's behavior/accessibility scaffolding at bystrek's current, tiny component count.
- **`ng-brutalism` (`@ng-brutalism/ui`, `khangtrannn/ng-brutalism`) (option A):** found via search — genuinely Angular-native, signals, zoneless, matches bystrek's stack philosophy, ships the exact aesthetic out of the box. Also would newly introduce Tailwind v4 into a `ui/` that currently has none. Rejected for now on dependency risk (young, single-maintainer, recently quiet) plus the added Tailwind buy-in — not rejected forever.
- **Option C won** because bystrek's UI is still small and minimal by design (point 3 above), the user already wants to prepare/compare multiple token-based theme variants (point 1) which C makes trivial with zero library opinion in the way, and it carries no new dependency risk. Matches the user's general preference for compiler-enforced, DI/service-layer-style control over adopting a framework's opinions ([[user_angular_background]]). Revisit Lion or `ng-brutalism` once the component surface actually grows past what hand-rolled tokens comfortably cover.

## Continuation: routing/layout restructure ahead of the visual pass (4th session, same day)

**Goal:** User surveyed real apps for inspiration (chat-first calendar assistants like Cal.ai/Daychat, neo-brutalist products like Gumroad/Figma), then asked for the current screen inventory before giving concrete restructure instructions: move `/login` under `/auth/login` alongside `/auth/reset-password`; make `/` a sidebar-shell layout (collapsed on mobile, expanded on desktop) with `/chat` as a full-screen child supporting markdown, and `/profile` reachable from the sidebar; add a real 404 page.

### What we decided

**Layout is a routed shell component (`features/layout`), not a wrapper directive or service.** `/` now loads `Layout` with `Main`/`Chat`/`Profile` as its router-outlet children, matching Angular's standard nested-route pattern for app shells — no custom abstraction needed.

**Markdown rendering: `marked` (parser) + `dompurify` (sanitizer), not a heavier Angular-specific markdown package (e.g. `ngx-markdown`).** Chat messages are LLM output rendered via `[innerHTML]`, so sanitization is mandatory, not optional — `marked.parse()` alone doesn't sanitize. Angular's own built-in sanitizer runs on top of the DOMPurify output as a second layer (belt-and-suspenders, since `[innerHTML]` bindings are always sanitized by Angular regardless of source). Picked the two-package combo over an all-in-one Angular wrapper because it's a smaller, more legible dependency footprint for what's really a two-line pure function (`core/chat/markdown.ts`).

**Removed now-redundant in-page navigation (Main's "Chat"/"Edit profile"/"Sign out" links, Profile's "Back" button, Chat's "Back" button) rather than keeping them alongside the new sidebar.** All of that navigation is superseded by the sidebar; keeping both would just reintroduce the "stitched-together" duplication the whole visual/UX effort is meant to fix.

**Scoped the old global centered-card CSS (`main { max-width: 360px; text-align: center }`, `body { display: flex; align-items: center; justify-content: center }`) to a new `.auth-shell` class instead of deleting it outright.** Login/reset-password/404 still want that centered-card treatment; Main/Chat/Profile, now living inside the sidebar shell, need to fill the content area instead. Bare-tag `main` selectors would have applied to both indiscriminately, so the fix was scoping via a class, applied only to the three auth-style screens.
