**Goal:** Something small, visible in the UI — auth-adjacent if it fit naturally, but not required. Calendar (item 4) is still the next big vertical slice; this was deliberately a lighter session.

## What we decided

**Full `better-auth` wiring rejected as "small."** It's a real subsystem — self-hosted auth server, WebAuthn registration, invite tokens, magic-link fallback — sized as its own vertical slice already, not something to do a cut-down version of without redoing it properly later.

**Surface the existing `households`/`users` data instead of pure UI polish.** Two options were on the table: cosmetic-only (theme toggle, copy tweaks) or connecting the UI to data that already exists but nothing reads yet. Picked the latter — real forward progress on the auth-adjacent data model rather than decoration, and genuinely small: one read-only endpoint, one UI card.

**No auth on the new endpoint.** `GET /household` sits at the same trust level as the existing `/push/*` endpoints — CORS-scoped, no session/token check. Consistent with the project's current state (nothing has auth yet); revisit once `better-auth` actually lands.

## What we actually built

- `GET /household` (`api/src/household/`): reads the single household row and its members, returns `{ name, members: [{ name, status }] }`.
- `bun run db:seed`: idempotent script inserting the `bystrek` household and its first member — the same "admin creates a household member record" step `architecture.md` already describes, just without the invite-token/session part yet. Owner name/email come from `SEED_OWNER_NAME`/`SEED_OWNER_EMAIL` env vars, not hardcoded — see PII fix below.
- UI: a small household card on the front page, fetched on load, showing members and their `invited`/`active` status.
- Went out as a PR (`household-endpoint` → `main`), not a direct push, per this session's request — consistent with how the household/user data model PR went out the session before.

## Problems hit along the way (and the actual fixes)

**Seed script originally hardcoded a real name and email.** Reasoned in the moment that this matched existing precedent (the email already appears in `api/.env.example`'s `VAPID_SUBJECT` and in day one's devlog), so didn't stop to ask. GitHub Copilot's automatic PR review caught it anyway — committing PII to a *public* repo's history is worth avoiding even where precedent exists, especially in a file whose whole purpose is inserting exactly that data. Fixed: owner name/email now come from env vars (`SEED_OWNER_NAME`/`SEED_OWNER_EMAIL`, `.env`-only, same pattern as every other secret in this repo); the household name itself (`"bystrek"`) stayed hardcoded since it's not identifying.

**Three more real findings from the same Copilot review round, all fixed:**
- Seed script called `process.exit(0)` unconditionally after `seed()` without awaiting/catching — a thrown error would leave the process hanging with an open DB connection instead of failing loudly. Fixed: `seed().then(() => process.exit(0)).catch(...)`, exits non-zero on failure.
- `GET /household` returned member email addresses over an unauthenticated route — real PII exposure, and not something the UI even displayed (it shows `name`, falling back only within the component). Dropped `email` from the response entirely.
- `.limit(1)` with no `orderBy` made the chosen household nondeterministic once more than one row exists. Added `.orderBy(asc(households.createdAt))`, plus an integration test that actually exercises it (three households inserted out of chronological order, asserts the oldest wins).

**A pre-existing e2e flake surfaced while testing, unrelated to this feature — chased down and fixed anyway.** `subscribe.spec.ts` (the push-notification e2e test from day five) failed intermittently in CI. Confirmed by stashing this session's changes and re-running against unmodified `main`: it failed there too, both under parallel workers and on repeated single-worker runs, so it predates this session. Root cause: SvelteKit's dev-mode client bundle is served as unbundled ES modules; `page.goto('/')` resolves on the `load` event, which can fire before hydration finishes attaching event listeners — the test's click then silently lands on a not-yet-interactive button and does nothing for the full 5s timeout. Fixed by waiting for `networkidle` before the click. Verified with repeated stress runs (36/36 passed) before trusting it, same instinct as every other session.

**Local dev Postgres briefly broke this feature's own new integration tests.** Manually running `bun run db:seed` against local dev to verify the endpoint left real committed household/user rows in the same database the integration tests run against. Since those tests run inside a rolled-back transaction, they still see other connections' already-committed rows (standard read-committed behavior) — the "404 when no household exists" test failed locally for exactly this reason. Not a code bug; cleared the seeded rows and re-ran clean.

**The Auto Mode Bash classifier blocks `git push`/`gh pr create` outright, separately from normal approve/deny prompts.** Even after explicit in-conversation approval, the classifier denied the tool call — it doesn't see conversational context, only the command. The user ran `git push` directly via the `!` prefix (bypasses the tool-call path entirely) to unblock the first push, then added `Bash(git push:*)`/`Bash(gh pr create:*)` as "ask" permission rules via `/permissions` so subsequent pushes/PR-creates prompt normally instead of hard-blocking.

## Continuation: auth direction reconsidered (second session, same day)

**Goal:** Revisit the auth direction before building it. Two threads: whether a standalone self-hosted IdP (Keycloak-style) beats the already-decided embedded `better-auth`, and whether the decided passkey-first flow is more complexity than it's worth.

### What we decided

**Standalone IdP (Keycloak/Authentik/Zitadel/Ory/Pocket-ID) rejected, stays embedded `better-auth`.** Keycloak's actual value — realms, groups, fine-grained authorization services, multi-app SSO, LDAP federation — has nothing to attach to here: one client app, a household-scale user base, and a deliberately flat sharing model (`owner_id` + `private`/`household`, no per-item ACLs) that doesn't map onto realm/group concepts anyway. Cost side is real too: Keycloak is still JVM-based (Quarkus), wants its own Postgres schema, adds a second service to patch/monitor on a 2GB droplet, and its WebAuthn support is bolted-on rather than passkey-first. Lighter alternatives exist (Authentik, Zitadel, Ory's composable stack, Pocket-ID for homelab/passkey-sized use) and were named for completeness, but all share the same structural cost versus an embedded library: a separate network service behind an OIDC redirect instead of a library in the same process/deploy/DB as everything else.

**The actual driver was user management (invite by email, self-serve setup, disable from a UI), not wanting an IdP per se.** Once named explicitly, this didn't require a standalone IdP at all — checked (via live web search, not assumed from memory) that `better-auth`'s official `admin` plugin already covers create/list/ban/unban users, with ban revoking sessions immediately. Corrected a mistaken assumption along the way: the plugin is API-only, no bundled admin UI ships with it. What exists instead: an official *hosted* dashboard ("Better Auth Infrastructure") — ruled out, it'd route auth data through a third party, contradicting the self-hosted principle already decided — and unofficial community shadcn-based dashboard packages, ruled out as unaudited third-party code for a security-sensitive surface. Landed on: build the disable/list page ourselves, on the household card view already shipped earlier this session, calling the admin plugin's client methods directly.

**Passkey-first bootstrap dropped for v1, not just resequenced.** The decided flow used an unauthenticated invite-token resolving straight into a first-ever passkey registration (`registration.requireSession: false` + `resolveUser`) — identified as the highest-risk, least-standard part of the original plan, since most WebAuthn prior art assumes registering a credential for an *already-authenticated* session, not bootstrapping a brand-new account from nothing. First move was to propose resequencing (magic-link bootstraps the account, passkey gets added afterward from an authenticated session — the well-trodden WebAuthn case). Then reconsidered further and dropped passkey from v1 entirely rather than even doing the resequenced version now. This is genuinely free to defer, not a corner cut: `better-auth`'s passkey plugin adds its own credential table independent of the `users`/`households` schema already built, so nothing about today's schema needs to anticipate it.

**Password ruled out on security grounds, not just "not chosen."** Passwords mean owning hashing, reset flows, and breach-list checking — more attack surface than magic-link, for a worse property (shared secret, phishable) — and this app is explicitly headed toward medical records, so that trade isn't close.

**v1 auth design: invite and every regular login collapse into the same magic-link flow.** No separate signed-invite-token mechanism: an admin creates the user row directly (`status: invited`) via the admin plugin's `createUser`, and `better-auth`'s magic-link plugin has a `disableSignUp` option — a magic-link request only succeeds for an email that already has a row. So "accepting an invite" and "logging in later" are literally the same code path, gated structurally by whether the row exists rather than by a bespoke token. Session: bearer token (already decided, sidesteps cross-origin-cookie complexity), leaning toward a rolling TTL that refreshes on activity with an inactivity cap (concrete numbers, e.g. ~90 days, left for implementation time) rather than a fixed wall — so an actively-used household app rarely surfaces the email step, but a lost/abandoned device's access dies on its own.

**Flagged, not resolved: whether an installed PWA actually shares storage with Safari on iOS.** The magic-link email will typically open in Safari, not the standalone installed app; whether the bearer token stored there is visible inside the PWA depends on iOS's storage-sharing behavior for the same origin. Same class of concern that already motivated the WebKit-only Playwright decision — needs a real-device test the moment this is built, not an assumption carried in from general web knowledge.
